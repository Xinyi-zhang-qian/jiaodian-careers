# ::work -algocheck 模板（算法正确性检查）

> 本文件为 `::work -algocheck` 的完整协议：「主 Agent 编排」节由主 Agent 执行；「Algocheck 子 Agent 协议」节由子 Agent 遵循。
> 由 `system/commands/work.md` 模板分派进入；写作规范与语言风格遵循 `AGENTS.md`。

---

## 主 Agent 编排

`::work -algocheck [@<文件或目录路径> ...] <custom prompt>`

核验指定算法在当前代码库中的**实际实现位置、适用边界与正确性**，并在 GitHub 上查找可比开源实现做源码级对照，产出检查报告。本模板**只检查与报告，不自动修复**：不改源码、不改测试、不改配置，发现错误后给修复建议即停止。

**参数**：

- `<custom prompt>`：**必填**。检查目标（算法名、计算功能或业务计算目标）与关注性质/边界。缺失时报错中止，不得默认泛扫全库。
- `@targets`：可选，可重复。仓库相对路径（文件或目录），用于收窄检查范围。不带 `@` 时以当前仓库为范围，按 prompt 定位算法。

**目标与原则**：

1. 先回答「算法在本库中负责什么、在哪里实现、在什么前提下承诺什么结果」，再判断正确性。
2. GitHub 是唯一外部来源；搜索是必须执行且留痕的阶段，找到可比实现才继续对比。
3. 每项结论必须附证据，并区分**静态推演**与**实际执行**；测试通过、多 Agent 意见一致均不等于算法已被证明正确。
4. 区分问题类型：算法逻辑/契约错误、数值行为问题（浮点误差、溢出、NaN）、性能/资源问题、规格不清/证据不足。数值误差只有违反明确误差界或结果契约时才算正确性缺陷；单纯性能差不叫计算结果错误（时限/内存上限本身属于契约时除外，需注明是哪条约束）。

**执行步骤**：

1. **解析与校验**：解析 `-algocheck` 标记、prompt 与 `@targets`。prompt 缺失 → 报错中止；逐一确认 `@` 路径存在，无效目标向用户报告，全部无效且任务依赖上下文时中止。
2. **确定输出路径**：默认 `workspace/algocheck-YYYY-MM-DD-HHMMSS.md`（`workspace/` 不存在时创建）；prompt 中用自然语言或 `--out <path>` 明确指定时使用该路径；目标已存在时换用新时间戳路径，不得覆盖已有报告。
3. **启动 algocheck 子 Agent**，注入固定上下文块：

   ```
   ORIGINAL_COMMAND: ::work -algocheck ...
   DATE: YYYY-MM-DD
   TIME: HH:MM:SS
   OUTPUT_FILE: workspace/algocheck-....md
   CUSTOM_PROMPT: <用户自定义提示原文>
   TARGETS: [{type: file|dir, path: ...} 列表，可为空]
   GIT_BASELINE: {git rev-parse HEAD 结果 或 "非 git 仓库/不可用"}
   启动指令：Read system/worker/templates/algocheck.md 并按「Algocheck 子 Agent 协议」执行
   ```

4. **主 Agent 独立复核**：子 Agent 返回后，对报告中的高影响发现（确认存在的错误、确认违背契约）逐项复核——触发条件是否在本库允许范围内、是否真的违反明确契约、调用方是否已排除该情况、反例推演是否成立。复核不通过的发现降级为「疑点，尚待验证」并在报告中注明复核意见。**只复核校验，不进入修复**。
5. **汇总输出**：向用户报告报告路径、审查算法数、确认问题数、待验证数、GitHub 对比状态与结论摘要。

**日志摘要**：`检查报告写入 {OUTPUT_FILE} | 审查算法 {N} | 确认问题 {N} | 待验证 {N} | GitHub对比: {已对比/已搜索无可比实现/未搜索/搜索失败} | 状态: {完成/部分完成/不适用}`

## Algocheck 子 Agent 协议

> 主 Agent 启动 algocheck 子 Agent 时，在 prompt 中注入固定上下文块，并指示其 Read 本文件、严格按本节执行。
> 工作目录为当前仓库根目录（`AGENTS.md` 所在目录）。

**角色**：算法正确性检查 Agent 由主 Agent 通过 `::work -algocheck` 命令启动，围绕 `CUSTOM_PROMPT` 指定的算法或计算目标，核验其在当前代码库中的实现位置与适用边界，执行 GitHub 开源实现对比，产出检查报告写入 `OUTPUT_FILE`。

**核心原则**：以代码与已确认契约为准；每项结论注明证据类型；找不到实现、找不到可比开源实现、规格缺失时如实说明，不得为满足流程编造检查对象或外部来源。

### 文件权限声明

**允许执行**
- 只读 shell 命令（`ls` / `find` / `grep` / `git log` / `git rev-parse` 等），用于定位实现与调用链
- `gh search repos` / `gh search code` / `gh api` / `gh repo view` 等**只读** `gh` 命令，用于 GitHub 检索与版本锁定
- `WebFetch`，用于打开 GitHub 仓库/源码页面核实内容

**允许读取**
- `TARGETS` 中注入的所有目标文件/目录
- 为定位与理解算法所必需的仓库文件：源码、测试、配置、依赖清单、`docs/`、`plans/`、`qna/`、`README.md`
- 本文件（`system/worker/templates/algocheck.md`，系 `system/` 禁读规则的明确例外，仅用于确认本协议）

**允许写入**
- `OUTPUT_FILE` 指定的路径（唯一写入目标）

**禁止**
- 修改任何源码、测试、配置、文档（含格式化、重命名、删除）；禁止 Git 写操作
- **禁止构建、运行测试、执行被检查代码或外部代码**（运行可能写缓存、装依赖、执行任意项目代码；动态验证需用户单独授权，未执行不得写成已通过）
- 读取 `local.md`；读取除本文件外的 `system/` 其他文件；访问仓库根目录之外的文件
- 向 GitHub 或任何外部服务发送本库源码、内部业务名称、未公开文档、数据样本或凭据——检索只使用公开技术关键词

### Step 0 — 解析参数

从 prompt 中提取主 Agent 注入的字段：`ORIGINAL_COMMAND`、`DATE` / `TIME`、`OUTPUT_FILE`、`CUSTOM_PROMPT`、`TARGETS`、`GIT_BASELINE`。

### Step 1 — 库内实现定位

根据 `CUSTOM_PROMPT` 定位算法。prompt 明确指定算法时只检查该算法及必要的调用方、数据结构与依赖；未指定具体算法时，先识别影响主要计算结果的关键算法，按「对主要结果的影响、公共接口覆盖、状态复杂度、测试薄弱处」选取少量重点对象（典型 1-3 个），并说明选取理由与未检查范围。

对每个算法必须定位（均需提供**文件:行号**）：

| 核验项 | 必须提供的证据 |
|---|---|
| 功能入口 | 用户/上层调用进入的文件、符号及行号 |
| 核心计算 | 实际执行算法的函数、方法或模块 |
| 调用链 | 入口 → 预处理 → 核心计算 → 后处理 → 结果输出的完整路径 |
| 分支实现 | 默认实现，以及配置、平台或数据类型触发的其他实现分支 |
| 外部依赖 | 委托给哪个库、哪个接口，项目锁定的版本 |
| 测试位置 | 对应测试文件与关键断言；未找到时明确注明 |

**找到同名实现还不够，必须核实实际调用路径是否使用它。** 未被调用的旧实现、备用实现、测试辅助实现分别标注，不混入主路径。依赖继续扩张（如核心计算又委托给下层库）时说明已核查到的层次与剩余不透明部分。

找不到对应实现时：报告标注「不适用：在所查范围内未定位到该算法实现」，说明已查范围，跳到 Step 6 输出报告，不得编造检查对象。

### Step 2 — 算法边界核验

为每个算法建立**边界清单**。每项边界记录三列：要求是什么、由谁保证、代码证据位置。

| 边界类别 | 核验内容 |
|---|---|
| 输入边界 | 类型、形状、取值范围、排序要求、是否允许空输入/重复值 |
| 输出约定 | 结果含义、顺序、并列结果选择规则、无解/失败时行为 |
| 数值边界 | 精度、舍入、整数溢出、无穷值、NaN、误差容许范围 |
| 状态边界 | 是否修改输入、跨调用状态、并发/重入限制 |
| 规模边界 | 递归深度、数据规模、内存与时间约束 |
| 异常边界 | 非法输入由谁拒绝、失败如何返回/抛出 |

「由谁保证」必须落入五类之一：**实现内部已检查 / 调用方已保证 / 文档声明但代码未保证 / 根据代码推断 / 未知**。核心算法依赖某个前提而实际调用链未保证它，本身就是需要报告的问题。

正确性标准优先采用用户明确需求与接口契约；**不得仅凭代码当前行为或现有测试预期值反推正确性**。规格缺失或冲突时，可提出假设做条件性分析，但标注为「契约缺失/冲突，待澄清」，不擅自决定业务规则。

### Step 3 — GitHub 搜索（唯一外部来源）

联网范围**仅限 GitHub**（仓库、代码、Issues、Releases）；不使用通用搜索引擎、博客、论文站、包站主页等其他来源。

1. **构造检索词**：基于 Step 1-2 的库内事实——算法名及可能别名、算法变体、问题定义、实现语言、关键输入前提或数据结构关键词。只使用公开技术术语。
2. **执行检索**：用 `gh search repos` / `gh search code` 检索，必要时 `WebFetch` 打开 GitHub 页面核实。记录实际使用过的关键词组合。
3. **候选筛选**：候选须满足——同一算法或同一明确变体、解决的问题与输入假设可比、能定位具体源码文件、能锁定版本。争取找到两个独立实现对照，但不凑数：fork 不算独立来源；只有调用示例而无核心实现、前提明显不同、同名不同语义的项目均排除并留痕。
4. **版本锁定**：正式纳入比较的每个实现记录——仓库 URL、完整 commit SHA（`gh api repos/{owner}/{repo}/commits/{branch}` 获取；无法锁定时注明「按访问时快照」）、tag/release（如有）、相关源码路径/符号/行号、访问日期、许可证（查 LICENSE 文件与文件头；未找到写「许可状态未核实，不建议复制」）。README、搜索摘要、star 数不能替代源码证据。
5. **失败与降级**：GitHub 不可访问、`gh` 未认证或检索报错时，记录失败方式后继续库内部分；外部对比状态标记「搜索失败」。

### Step 4 — 开源实现源码对比（存在可比实现时）

逐算法形成对照表，比较**行为与前提**而非代码相似度：

| 对比项 | 本库实现 | GitHub 参考 |
|---|---|---|
| 算法名及变体 | 实际实现语义 | 源码确认的语义 |
| 输入前提 | 本库边界（Step 2） | 参考实现边界 |
| 核心步骤 | 分支、状态与更新顺序 | 对应实现 |
| 边界处理 | 空输入/重复/极值/无解等 | 对应处理 |
| 数值行为 | 溢出、精度、舍入 | 对应策略 |
| 输出语义 | 顺序、并列结果、失败返回 | 对应行为 |
| 测试覆盖 | 本库已有断言 | 参考的边界用例 |

每条差异分类为：**业务定制 / 前提不同不可直接比较 / 等价写法 / 可能影响正确性 / 确认违背要求 / 证据不足**。GitHub 实现是对照证据而非标准答案：两边一致可能共享错误，两边不一致也可能只是并列结果选择规则不同。

对「可能影响正确性」的差异继续分析：指出本库应满足的具体要求 → 确认触发条件能否从真实入口到达 → 构造最小输入或状态变化过程 → 写出预期结果及依据 → 写出本库实际行为（静态推演须明确标注「未运行」）。

### Step 5 — 撰写报告

将报告写入 `OUTPUT_FILE`（目录不存在时创建），固定七节结构：

```markdown
# 算法正确性检查报告：{算法/主题}

> 检查命令：{ORIGINAL_COMMAND}
> 代码基线：{GIT_BASELINE} | 检查时间：{DATE} {TIME}

## 1. 结论摘要
{直接回答 CUSTOM_PROMPT；注明结论适用范围与 GitHub 对比状态}

## 2. 本库实现地图
{逐算法：功能入口、核心实现、调用链、分支实现、外部依赖、测试位置，均带文件:行号}

## 3. 算法边界清单
{逐算法：输入/输出/数值/状态/规模/异常边界，每项含要求、保证方、代码证据}

## 4. GitHub 搜索记录
{检索词组合；候选清单及选用/排除理由；纳入比较者的仓库 URL、commit SHA、源码位置、许可证、访问日期}

## 5. 开源对比或跳过说明
{有可比实现：对照表与差异分类；无：四状态之一（已对比/已搜索无可比实现/未搜索/搜索失败）及理由}

## 6. 问题与验证证据
{逐问题：位置（文件:行号）、前提、最小反例输入/轨迹、预期与实际或推演结果、影响、问题类型（逻辑/数值/性能/规格不清）、证据类型（静态推演/实际执行）、修复建议（只建议不实施）}

## 7. 未完成项与影响
{规格缺口、不可见依赖、未覆盖范围、外部证据缺失对结论强度的影响、停止原因}
```

写作要求：全部使用中文，代码与符号名保留原文；区分「已阅读的测试 / 手工推演 / 实际执行的验证 / 建议但未执行的验证」，未执行不得写成通过；性能与结果正确性分开记录。

### Step 6 — 结论分级与完成信号

每个算法的结论落入以下之一（可多算法各自不同）：

- **确认存在错误**：有明确契约 + 可核查的逻辑推导或反例（注明静态推演还是实际执行）；
- **疑点，尚待验证**：已定位可疑路径但证据不完整；
- **范围内未发现问题**：必须注明检查范围、方法，以及是否含 GitHub 对比；不得宣称算法普遍正确；
- **无法判断**：规格缺失/冲突、依赖不可见；
- **不适用**：库内未定位到实现。

外部对比四状态：**已对比 / 已搜索无可比实现 / 未搜索 / 搜索失败**。找到实现但均不可比时写「已搜索无可比实现」并列排除理由；**不得**表述为「不存在相关开源实现」或「与开源最佳实践一致」；此状态下结论强度仅限库内证据支持的部分。

完成信号：

```
[ALGOCHECK_DONE]
output_file: {OUTPUT_FILE}
algorithms: [{算法1}, {算法2}, ...]
confirmed_issues: {N}
pending_issues: {N}
github_status: {已对比 / 已搜索无可比实现 / 未搜索 / 搜索失败}
stop_reason: {完成 / 部分完成（原因）/ 不适用}
[/ALGOCHECK_DONE]
```

然后**立即退出**，不得再调用任何工具。完成信号表示检查流程结束，不代表算法已通过验证。

### 停止条件

- `CUSTOM_PROMPT` 缺失、目标全部无效 → 主 Agent 中止并说明；
- 未找到算法实现 → 标记「不适用」，报告已查范围；
- 契约缺失或相互冲突 → 该项停止确定性判定，列出待澄清问题；
- 发现明确反例 → 保存证据后继续其余范围，**不进入修复循环**；
- 范围或工具预算耗尽 → 标记「部分完成」，列出未覆盖项；
- 需要新增权限（运行动态验证、安装依赖、访问仓库外文件）→ 在报告中列为待授权事项，不擅自执行；
- 检查期间代码基线变化（与 `GIT_BASELINE` 不一致）→ 在报告中注明并标注受影响证据；
- 用户明确要求全程只读（不落盘）时 → 跳过 Step 5 写文件，直接以完成信号附报告全文返回。
