# ::devplan

> 命令索引见 `system/command_reference.md`。本文件为 `::devplan` 的完整执行协议。

---

## `::devplan [修改意见]`

开发计划命令。确定本轮要实现/修改的模块，建立或修改模块级接口/测试文档，制定全部文件（代码 + 文档）的修改计划，输出到 `plans/current.md` 并等待用户批准。由主 Agent 直接执行。

**参数格式**：
- `[修改意见]`：可选。用户对上一轮计划的修改意见；存在时据此调整计划并重新输出（重复本命令直到用户批准）。

**前置条件**：`docs/requirements.md`、`docs/design.md` 与 `docs/interaction.md` 存在且已批准。

**fast 模式**（由 `::init -fast` 进入，`status.md` 的 `[Fast Baseline]` 非空）：全局文档已存在且**只读**——本命令以 `::init -fast` 的 custom prompt 与现行全局文档为输入，计划只写本轮 diff，修改清单**不得包含** `docs/requirements.md`、`docs/design.md`、`docs/interaction.md` 的修改项（全局文档欠账由 `::devlog` 记录、`::doc` 追赶）；模块文档（`docs/modules/`）与 `docs/test.md` 照常建立与修改。

**手动调用检查（门禁）**：本命令由用户手动调用时，先执行 `system/command_reference.md` 的「阶段门禁与手动调用提醒」：读 `status.md` 的 `[Current Phase]` 与 `[Phase History]`，向用户报告上一阶段（需求分析）的完成情况与本次调用的性质；需求文档/设计文档缺失或未批准时，提醒用户先回到 `::req` / `::design`（全自动情景除外，直接提示后按现状可行范围执行或中止）。若本次计划调整意味着整体设计改变，提醒用户应先走 `::design` 以忠实执行打断归档。

**执行步骤**

**步骤 0 — 中断续接检查**：`docs/archive/` 下存在中断归档时，先读最近一次 `interruption.md` 清单。本轮计划必须显式承接：哪些已完成模块直接复用（不重做）、哪些半成品模块从清单记录的状态继续（写明剩余工作）、清单中的残留文件如何处置（删除/改造/保留），避免程序混乱与重复开发。

**步骤 1 — 确定模块范围**：对照 `docs/design.md` 的模块划分与当前代码现状，确定本轮需要**实现**（新增）与**修改**（已有）的模块清单。

**步骤 2 — 建立/修改模块级文档**（按需生成，一个模块两份）：
- `docs/modules/{模块名}_design.md` 与 `docs/modules/{模块名}_interaction.md`：模块设计文档与模块交互文档，内容与深度以 `system/commands/dev.md` 的「模块文档规范」为权威（模块内部结构与数据流归设计文档；逐接口的输入/输出/边界检查/错误处理归交互文档；全局文档已定义的只引用不重复）。建立时按本轮计划写目标状态；发现全局契约冲突或缺失时停下并提示回到 `::design`。
- 不建立模块级测试文档——全部测试集中注册于 `docs/test.md`（规范见 `system/commands/dev.md`「测试文档规范」），本轮拟新增/修改的测试列入计划 checklist，由 `::dev` 登记。
- 已存在的模块文档按本轮变更修改（保持与计划一致）。

**步骤 3 — 归档旧计划**：`plans/current.md` 已有内容时，按本文件下文「计划文档管理规范」将全部内容移入 `plans/YYYY-MM-DD.md`（日期取旧计划创建日期，无法确定时取当天；已存在则追加）。

**步骤 4 — 撰写新计划**写入 `plans/current.md`，只展示本轮 diff 部分（不重复已批准且无变化的内容），结构为五段：

```markdown
# 当前计划 — {本轮主题}

创建日期：YYYY-MM-DD
状态：待用户批准

## 1. 核心功能
（继承自人类需求）系统或本轮修改实现的核心功能是什么。

## 2. 接口与测试
（继承自交互设计和测试设计）用户（含运行时依赖环境）可以用哪些接口与系统交互；
交互结果的预期行为；已经实现了哪些测试；还需要添加什么测试。

## 3. 模块划分
系统有哪些模块；本轮修改涉及哪些模块（新增/修改/不动）；
模块之间的耦合关系（引用 docs/design.md 的模块正式定义，不再重复展开）。

## 4. 模块间接口与数据流
本轮涉及的模块间接口变化；数据如何在模块间流动（只写 diff）。

## 5. 模块内数据流
本轮涉及模块的内部数据流设计（高内聚：输入 → 处理链 → 输出）。

## 修改清单
### 代码
- {文件路径}：{改动说明}
### 文档
- {文档路径}：{改动说明}

## Checklist
- [ ] {模块A}：{实现/修改内容}
- [ ] {模块B}：...
- [ ] 模块间级和整库级的整合测试
```

**步骤 5 — 等待批准**：向用户展示计划（重点展示 diff 部分），等待批准；用户要求修改则回到步骤 1 重复本命令；批准后更新 `status.md`：`[Current Phase]` 置为 `模块开发`，并向 `[Phase History]` 本轮行追加 `开发计划（{YYYY-MM-DD HH:MM}）`；提示执行 `::dev`。

**规则**：
- Checklist 最后一项默认固定为「模块间级和整库级的整合测试」。
- 模块文档与计划必须一致：checklist 中每个模块都能在 `docs/modules/` 找到对应设计/交互文档（`{模块}_design.md` 与 `{模块}_interaction.md`）；模块文档引用全局设计/交互文档而不重复其内容。
- 继承全局契约与验收引用：模块文档引用 `docs/design.md` 的架构契约与 `docs/interaction.md` 的交互规格，只写模块内部设计；契约冲突或缺失回到 `::design` 解决，不在模块文档悄悄另定默认值。
- 计划中禁止写入真实凭据等敏感信息。

## 计划文档管理规范

`plans/` 目录与 `plans/current.md` 的管理规则由本命令定义；当用户要求进行计划或进入 Plan Mode 时，同样按本规范更新 `plans/current.md`。

- 在仓库根目录维护 `plans/` 文件夹，集中存放项目计划文档。
- `plans/current.md` 只存放当下这一轮的计划；每次执行工作前必须先读取 `plans/current.md`。
- 每次写入新计划时，将旧 `current.md` 的全部内容移入对应日期的归档文件 `plans/YYYY-MM-DD.md`（日期取旧计划的创建日期，无法确定时取当天日期）；若该日期的归档文件已存在则追加内容。除非用户明确说保留，否则不得在 `current.md` 中遗留旧计划内容。
- 更新计划或开始执行前，需先向用户询问具体细节，确认后再继续（`/goal ::init` 等全自动情景除外）。

## 运行日志

本命令执行完毕后，必须向仓库根目录 `system_log.md` 追加一条记录：

````markdown
## [YYYY-MM-DD HH:MM:SS] {命令原文}
- 开发计划写入 plans/current.md | 涉及模块: [{...}] | 旧计划归档至 {plans/YYYY-MM-DD.md 或 无} | 中断续接: {loop{N} 或 无} | 状态: {等待批准/已批准}
````
