# ::lint

> 命令索引见 `system/command_reference.md`。本文件为 `::lint` 的完整执行协议。

---

## `::lint` / `::lint -hard`

代码质量检查与系统文档健康检查。采用「**主 Agent 编排 + 后台子 Agent 执行**」模式：扫描与检查（及 `-hard` 模式的改写）派发后台子 Agent 并行执行；主 Agent 全程独立负责——确定基准、注入上下文、独立校验子 Agent 报告（不直接采信）、汇总展示、用户确认、修复执行、回归验证、状态与日志更新。

**参数格式**（由主 Agent 使用 LLM 能力直接解析）：
- `::lint`：普通模式。代码质量四类扫描（检查并修复）+ 文档健康八类检查（只输出建议，「过时表述」类例外可修复）。**开发 loop 的代码检查阶段固定使用本模式**；`/goal ::init` 全自动 loop 中不得使用 `-hard`。
- `::lint -hard`：文档深度专项。在普通模式全部检查之上，追加三道改写工序——「库级文档只保留当前软件状态」（章节级清除）、「表达精简」（句子级压缩，内容不变）与「语言风格」（句子级改写，依据 `AGENTS.md`「全局语言风格」节）——以及一道「测试覆盖度审计」（对照全部交互文档——`docs/interaction.md` 与 `docs/modules/` 各模块交互文档——核查全部测试的覆盖程度：交互行为未被覆盖则补测试，测试冗余则删除，见第三部分 3.4）。仅当用户显式以 `-hard` 调用时执行。

**触发场景**：开发 loop 的代码检查阶段（`::mergelocal` 完成后由流程自然进入，普通模式）；用户随时主动调用（普通或 `-hard`）。本命令是阶段门禁的**豁免命令**，手动调用时不做「阶段门禁与手动调用提醒」。

**状态更新**：进入时若处于 loop 流程中，将 `status.md` 的 `[Current Phase]` 置为 `代码检查`；全部完成后，向 `[Phase History]` 本轮行追加 `代码检查（{YYYY-MM-DD HH:MM}）`，并提示执行 `::ci`。

## 第一部分：编排流程（主 Agent，逐步执行不得跳步）

**步骤 1 — 状态与基准准备（主 Agent 亲自执行）**：
- loop 流程中：将 `status.md` 的 `[Current Phase]` 置为 `代码检查`。
- 完整读取 `docs/requirements.md` 与 `docs/design.md`，列出全部已批准功能与模块接口清单，作为判定「多余功能」的基准（注入代码扫描子 Agent）。
- 建立两份扫描清单：
  - **业务源码清单**：全部业务源码文件；排除 `system/`、文档目录（`docs/`、`plans/`、`qna/`、`workspace/`）、测试目录中的测试辅助代码。
  - **文档清单**：纳入 `AGENTS.md`、`README.md`、`system/command_reference.md`、`status.md`、`system/commands/*.md`（含各命令的「子 Agent 执行协议」节）、`system/worker/**/*.md`（子 Agent 协议与模板文件）、`docs/`（含 `docs/modules/`）、`plans/current.md`；排除 `local.md`（含敏感信息）、`system_log.md`（append-only 日志）、`plans/` 日期归档、`qna/`、`workspace/`；`docs/archive/` 仅中断残留检查时读取。

**步骤 2 — 分组并派发后台子 Agent**：

分组与派发原则（必须遵守）：

| 原则 | 执行口径 |
| --- | --- |
| 单文件单 Agent | 同一文件绝不并行派发两个子 Agent，避免写冲突 |
| 大文件独立派发 | 超过 4000 行的文件单独分配一个子 Agent |
| 小文件按主题分组 | 同主题小文件打包给一个子 Agent（如「需求 + 测试 + README」一组） |
| 并行上限 | 遵守 `AGENTS.md` 全局并行调用限制，超出分批，等待该批全部返回后再发起下一批 |

- 每个子 Agent 注入固定上下文块（`ORIGINAL_COMMAND` / `DATE` / `TIME` / `MODE` / `TARGETS` / `BASELINE`），并指示其 Read 本文件「子 Agent 执行协议（linter）」一节执行；产出 `[LINT_DONE]` 完成信号后立即退出。
- 普通模式：`MODE=scan`——只读扫描与报告，子 Agent 禁止任何写入。
- `-hard` 模式：先以 `MODE=scan` 完成普通模式全部检查，再按第三部分分三道独立改写工序派发 `MODE=hard-edit`（按允许/严禁清单改写注入的指定文件），最后以 `MODE=scan` 派发测试覆盖度审计（第三部分 3.4），审计结论由主 Agent 核实后处置。

**步骤 3 — 主 Agent 独立校验（子 Agent 报告不算数）**：

子 Agent 的完成信号只作线索；实际结论与改动一律由主 Agent 以 git HEAD 为基线独立核实：

1. 逐条抽读被报告位置的原文，剔除失效与误报条目；
2. 以 `git diff --stat` 与抽读比对落盘的实际改动——报告失败 ≠ 没改动，报告成功 ≠ 改动合规，不得依据报告直接采信；
3. `-hard` 改写后追加执行第三部分 3.6 的全部校验项；测试覆盖度审计的问题清单逐条抽读核实（对照交互规格原文与测试断言）后再处置；
4. 子 Agent 启动失败或部分执行后失败：主 Agent 亲自接手该部分工作；接手前先核查对应文件是否已有部分改动落盘（`git status` / `git diff`），按落盘实际状态决定续做或重派，避免重复改或留半成品。

**步骤 4 — 汇总并展示问题清单**：按「输出格式」汇总（代码质量按四类分组，每项含 `文件:行号 + 问题描述 + 处置建议`）。非全自动情景下等待用户确认后才执行修复；全自动情景直接修复。

**步骤 5 — 执行修复（主 Agent 亲自执行）**：按确认的清单逐项删除/清理代码问题，每完成一项立即核对没有误删仍被引用的代码；「过时表述」类按确认直接改写文档；其余文档健康类只输出建议，**不修改文档**。

**步骤 6 — 回归验证（主 Agent）**：清理完成后运行受影响模块的模块内测试；全部通过则继续，有任何回归则回退对应修复项并向用户报告。

**步骤 7 — 收尾（主 Agent）**：输出修复报告（每项一行：位置、类别、处置结果）；向 `[Phase History]` 本轮行追加履历；提示执行 `::ci`；按本文件末尾模板追加运行日志。

## 第二部分：检查规则（子 Agent 扫描依据）

### 2.1 代码质量（四类，可修复）

| 类别 | 内容 |
| --- | --- |
| 多余功能 | 实现了但未被任何需求/接口/调用方使用的功能（超出 `docs/requirements.md` 与 `docs/design.md` 的范围） |
| 未删除的旧代码 | 被重构取代但未删除的旧实现、被注释掉的代码块、无人引用的函数/类/文件 |
| 过多防御性代码 | 对不可能发生的内部状态做的检查、重复的参数校验（公共边界校验保留，模块内部重复防御删除）、无意义的 try/except 包裹 |
| 死代码 | 不可达分支、永远为假的条件、未使用的 import/变量 |

**扫描要点**（对清单中的每个文件按四类逐一检查）：
1. **多余功能**：逐个功能/接口对照基准清单，凡不在基准内且无调用方的，记为多余功能；
2. **未删除的旧代码**：搜索被注释的代码块、带 `old/deprecated/legacy/backup` 等痕迹的函数与文件、被新实现取代的旧实现，逐个确认无引用后记入；
3. **过多防御性代码**：逐个 try/except 与参数校验判断其防护的状态是否可能由模块内部产生——不可能产生的内部防御记入；公共边界（CLI 入口、外部输入、跨模块接口）的校验**保留**；
4. **死代码**：检查不可达分支（return/raise 之后的代码、永远为假的条件）、未使用的 import 与变量。

### 2.2 文档健康（八类，只建议）

| 类别 | 内容 |
| --- | --- |
| 矛盾 | 同一定义（命令行为、字段名、路径、模块名、接口签名）在多个文件中出现且不一致；报告时列出各处原文 |
| 冗余 | 权威源文件（协议文件、设计文档）中的流程/字段细节在其他活跃文件中被同等粒度重复展开；建议改为指针引用。**特殊豁免**：`AGENTS.md` ↔ `README.md` 间的功能性重复允许存在，不报为冗余 |
| 残留 | 对照 git 历史与文档当前状态，已删除/重命名的概念、命令、路径在活跃文件中仍有出现；例如已弃用的 `CLAUDE.md` / `CLAUDE.local.md` / `sync_agents_md.py`（现名 `AGENTS.md` / `local.md`）、已移除的 `::explore` 独立命令（现为 `::work -explore` 模板） |
| 过时表述 | 「之前…现在…」「旧版…新版…」「原为…现改为…」等向后兼容措辞，以及对已被取代的旧状态、旧规则、旧结构的描述——活跃文档必须只写当前状态。**例外条款：可直接修复**（展示片段清单获确认后改写；全自动情景直接修复并报告） |
| 命令一致性 | 四处对齐——`AGENTS.md` 命令系统章节、`README.md` 命令速查、`system/command_reference.md` 索引表、`system/commands/` 文件集合（命令名、说明、数量；含 `::work` 的 `-模版` 可选值与 `system/worker/templates/` 文件集合一致） |
| 文档同步 | 对照代码现状核对 `docs/requirements.md`、`docs/design.md`、`docs/interaction.md`、`docs/test.md`、`docs/modules/`——接口签名与实现一致、模块清单与源码目录一致、测试条目与最近运行结果一致；**`docs/test.md` 登记与实际测试双向一致**——每条登记条目能定位到真实存在的测试（其「如何运行」可执行），且代码库中的全部测试均已登记到 test.md 对应小节（登记缺失补登记、登记无对应测试删条目；需新增或删除测试代码才能一致的，报告后再修复）。**发现不一致时按「不一致采纳优先级」（`system/command_reference.md`）确定权威方：权威方不动，直接修正非权威方文档（本类因此属可修复例外，与「过时表述」同类）；需要修改代码才能一致时向用户报告偏差后再修复** |
| 设计一致性 | `docs/design.md` ↔ `docs/interaction.md` 双向核对——每个 CLI 命令域能落到某个模块；每个用户可见功能有交互入口；GUI 章节与映射总表只引用已定义的 CLI 命令、无绕过 CLI 的直接业务操作；两份文档无冲突定义（全局交互协议唯一定义于 interaction.md）；交互规格四要素（预期输入/预期输出/边界检查/错误处理）完整；未决项明确（检查清单详见 `system/commands/design.md` 的「设计文档一致性检查」一节）。两份文档冲突时按「不一致采纳优先级」处理：需求文档可裁决的以需求文档为准修正，需求未覆盖的向用户报告 |
| 中断残留 | 读取 `docs/archive/` 下各 `interruption.md`，逐个核对「残留文件清单」中的文件是否仍存在且未被任何业务代码或活跃文档引用——仍存在且未使用者报告为残留并建议删除或并入新计划 |

## 第三部分：`-hard` 文档深度专项

> 在普通模式全部检查完成后，按「3.1 只保留当前状态 → 3.2 表达精简 → 3.3 语言风格」三道独立改写工序顺序执行（句子级工序在章节级删除稳定后进行），随后执行 3.4 测试覆盖度审计。三道改写工序共用 3.5 工具要求与 3.6 校验要求；改写由 `MODE=hard-edit` 子 Agent 执行，校验与审计结论核实由主 Agent 独立执行。

### 3.1 库级文档只保留当前软件状态

**适用文件**——以下文档全部只描述当前软件的需求与相关信息：`docs/requirements.md`、`docs/design.md`、`docs/interaction.md`、`docs/test.md`、`docs/modules/` 全部模块文档、`README.md`、以及项目自建的库级验证/环境记录文档。

**必须清除的叙述类别**（历史版本由 git 保存，不在文档中追溯）：

| 类别 | 说明 |
| --- | --- |
| 历轮「轮次增量 / 后增量」章节 | 逐轮追加的增量叙述全部删除；阶段路线图压缩为当前交付范围声明 |
| 「实现偏差说明 / 设计修订说明」类附录 | 附录与全部轮次出处标注一并删除 |
| 历轮出处与变更叙述 | 「删除 / 修复前后」类变更叙述一律清除 |
| 被取代的旧形态描述 | 旧区域划分、已删除控件、旧命令名等不再存在的形态 |
| bug 修复前后的「现状缺口 / 修正前 / 旧实现」叙述 | 一律改写为对当前设计/行为的直接陈述 |
| 历轮测试结果段 | 测试文档仅保留最新一轮结果 |
| 历史验证记录 | 环境/真机验证记录压缩为「验证事实」 |

- 「开发轮次规划」章节按设计协议**保留**，但只写当前交付状态：轮次总数、完成情况、四阶段归纳，不逐轮展开（轮次规划唯一定义于 `docs/design.md`，`docs/interaction.md` 不含此章）。

### 3.2 表达精简（内容不变，只删表达冗余）

**允许的修改**：
- 删除冗余引导语与套话。
- 合并同义重复的句子或重复块（保留交叉引用）。
- 压缩啰嗦句式（「进行 X 的操作」→「X」）。
- 删除可有可无的虚词。
- 把 bullet 条目内无语义作用的硬换行并句。
- 把纯枚举列表转为行内列举（清单项逐项保留，不得丢项）。

**严禁的修改**（逐条执行，宁可少改不可改坏）：
- 改变任何技术事实：接口签名、字段名、命令名、路径、数字、状态名、错误码、章节编号。
- 删改代码块内容：代码、伪代码、ASCII 图、协议帧格式、示例输出一律原样；代码围栏数量与配对保持不变。
- 删改表格行数与单元格数据。
- 删除或合并章节（章节结构与编号不动，只动章内表达）。
- 删改需求与验收条目的规范含义：「必须 / 应 / 不得」的规范强度不得变化。
- 新增信息，或使用「（略）」类元注释。
- 把文风改成电报体或要点碎片；精简后的句子必须仍是完整、可独立理解的句子。

**质量口径**：质量优先，不强凑百分比——代码块占比高的文档可压散文有限，压缩率不足时如实报告即可。

### 3.3 语言风格

**适用文件**：与 3.1 相同。

**改写依据**：`AGENTS.md`「全局语言风格」节为唯一权威。逐句检查并改写：

| 类别 | 改写口径 |
| --- | --- |
| 防御性表述 | 删除为尚未发生的误解做的反复辩解、主动罗列的用户未问且不影响决策的限制与免责声明、「并不是……而是……」式预设立场；确实影响判断的风险、限制或不确定性保留，但只写具体原因及影响 |
| 黑话与空话 | 删除或改写「赋能、抓手、闭环、对齐、沉淀、底层逻辑」等商业黑话与「范式、表征、解构、认知框架」等学术包装词；删去不增加信息的客套、铺垫、重复总结与自我评价；改写为「谁做什么、解决什么问题、结果是什么」的具体陈述 |
| 术语解释 | 专业术语、缩写或外文词首次出现未就地说明的，补充一句话解释（它是什么、在当前问题中有什么用；仅列英文全称不算解释）；读者可认为已了解本领域基础术语，已明确解释过的概念不重复解释 |
| 图表解释 | 表格或实验结果图出现而未先说明的，补一段完整的话描述该表格或图片的意义与解读方法，并逐项解释表格每一行、图例与标题中的非常识性内容 |
| 句子语法 | 随意减少成分的残句补全为符合正常汉语的完整成分句；过度嵌套的复杂句式拆分为简单句 |
| 简写和译文 | 删除或改写无含义的晦涩代号（几个字母数字组合或奇怪的中文名字）；非专业名词的外文表述按意思改为最贴切的中文译法 |
| 其他规范细节 | 解释缺少理解所必需的中间步骤时补齐（保证信息充分前提下尽可能简洁）；语境中易歧义的词写清楚主体和客体 |

**严禁的修改**：沿用 3.2「严禁的修改」全部条款（技术事实、代码块、表格行数、章节结构与规范强度不变）；术语解释以一句话为限，不得扩写为新章节。

### 3.4 测试覆盖度审计（对照全部交互文档）

**目的**：核验全部测试对全部交互文档的覆盖程度——`docs/interaction.md`（用户交互与模块间交互线）与 `docs/modules/` 各模块交互文档（逐接口规格）中的每条交互规格都必须被测试覆盖（未覆盖则补测试），测试不得冗余（冗余则删测试）。`docs/test.md` 头部约束已要求每条测试可回溯到某条交互规格，本工序对该约束做全量核查。

**执行方式**：三道改写工序完成后，派发 `MODE=scan` 子 Agent 执行只读审计，`TARGETS` 注入 `docs/interaction.md`、`docs/modules/` 全部模块交互文档、`docs/test.md` 与全部测试代码所在目录；子 Agent 产出覆盖映射与问题清单，主 Agent 按第一部分步骤 3 独立核实（抽读交互规格原文与对应测试断言，不直接采信报告）后再处置。

**判定口径**：
- **未覆盖**：`docs/interaction.md` 的逐命令/逐控件交互规格与模块间交互线、`docs/modules/` 各模块交互文档的逐接口规格（含预期输入、预期输出、边界检查、错误处理各要素的关键分支）没有任何测试的断言与之对应 → 记为未覆盖；模块交互文档中的每个接口都在核查范围内，不得只核查全局交互文档；
- **冗余**：同一交互规格的同一验证点被多条断言范围实质相同的测试重复覆盖（无不同边界或错误分支的区分），或某条测试无法回溯到任何交互规格 → 记为冗余测试。

**处置**（主 Agent 执行）：
- 未覆盖 → 按 `system/commands/dev.md`「测试文档规范」先把新测试登记到 `docs/test.md` 对应小节，再补写测试代码并执行通过；
- 冗余 → 删除多余测试代码，并同步删除 `docs/test.md` 中的对应登记条目；
- 处置完成后运行受影响的测试确认全部通过；审计与处置结果计入输出报告的「-hard 专项」节。

### 3.5 工具要求

- 必须先用 Read 工具**全量**读取被改文件（长文件分段读完），再用 Edit 工具**逐处**修改。
- **禁止**用 python/bash 脚本批量改写文档（脚本仅允许用于校验与统计）。

### 3.6 改写后主 Agent 校验（六项，子 Agent 报告不算数）

1. **不变量校验**：逐文件比对 git HEAD——标题集合、代码围栏数与配对、表格行数、bullet 数、数字 multiset、行内代码标识符 multiset。
2. **交叉引用校验**：全库「需求 §X / design §X / interaction §X」引用有效性逐一验证，零失效。
3. **清零扫描**：旧形态关键词与变更史措辞（「修正前 / 旧实现 / 现状缺口 / 零变更 / 行为不变」等）全库零命中；语言风格工序后再做风格清零——黑话与宣传腔词表（赋能 / 抓手 / 闭环 / 对齐 / 沉淀 / 底层逻辑 / 范式 / 表征 / 解构 / 认知框架 等）在改写对象文件中零命中（规则引用处除外）。
4. **围栏配对**：Markdown 代码围栏开合配对全通过。
5. **差异定级**：对检出的每一处差异逐项判定——良性（去重副本 / 引用重排）放行并记录说明；发现内容损失（实质问题）必须当场修复。
6. **回归**：完成后运行受影响模块的测试，确认文档改动无代码回归。

### 3.7 改写子 Agent prompt 固定要素（六段）

派发 `MODE=hard-edit` 子 Agent 时 prompt 必须包含以下六段：

```text
1. 任务背景与目标（一段话）
   说明本次改写主题（3.1 或 3.2）、依据的规范与预期效果。
2. 强制工具要求
   - Read 全量读取（分段读完）+ Edit 逐处修改；
   - 禁止 python/bash 脚本批量改写；
   - 禁止任何 git 写操作；
   - 只允许改动注入的指定文件清单。
3. 「允许的精简/修改」清单
   逐条列出（3.1 工序列清除类别；3.2 工序列「允许」清单；3.3 工序列语言风格改写口径）。
4. 「严格禁止」清单
   逐条列出禁改对象（3.2「严禁」清单，含禁删对象明细）。
5. 风格要求
   中文输出、保持原文笔调、句子完整、列表与标点风格不变。
6. 目标与产出报告
   报告前后行数、修改处数、2–3 组前后对照示例、
   放弃改动/有风险的位置清单，并对改动范围做显式确认。
```

## 子 Agent 执行协议（linter）

> 主 Agent 启动 linter 子 Agent 时，在 prompt 中注入固定上下文块，并指示其 Read 本文件、严格按本节执行。
> 工作目录为项目根目录（`AGENTS.md` 所在目录）。
> 写作规范（中文输出、严禁编造、严禁向后兼容措辞）与语言风格遵循 `AGENTS.md`。

**角色**：linter 子 Agent 由主 Agent 通过 `::lint` 命令以后台方式启动，按注入的 `MODE` 执行——`scan`：对注入目标做只读扫描并报告问题；`hard-edit`：按允许/严禁清单改写注入的指定文件。

**核心原则**：只处理注入 `TARGETS` 中的文件；只依据 `BASELINE` 与本文件第二、三部分的规则判定问题；不得超出注入范围行动。

### 文件权限声明

**允许执行**
- 只读 shell 命令（`ls` / `find` / `grep` 等），用于探索与定位

**允许读取**
- `TARGETS` 中注入的所有文件
- `BASELINE` 指向的基准文档（`docs/requirements.md`、`docs/design.md`）
- 为判定问题所必需的其他仓库文件（被目标代码 import 的依赖文件、`docs/archive/` 下的中断清单等）

**允许写入**
- `MODE=scan`：禁止写入任何文件（只读扫描）。
- `MODE=hard-edit`：仅允许用 Edit 工具逐处修改 `TARGETS` 中注入的文件（唯一写入对象）。

**禁止访问**
- `local.md`（含敏感信息）、`status.md`、`system_log.md`
- 仓库根目录之外的任何文件
- 禁止执行任何修改仓库状态的命令（git 写操作、构建、测试运行等）；`MODE=scan` 另禁止一切写入

### Step 0 — 解析参数

从 prompt 中提取主 Agent 注入的字段：

- `ORIGINAL_COMMAND`：用户输入的完整命令原文。
- `DATE` / `TIME`：当前日期与时间。
- `MODE`：`scan` 或 `hard-edit`。
- `TARGETS`：本次负责的文件清单（扫描对象或改写对象）。
- `BASELINE`：判定基准说明（已批准功能与模块接口清单摘要，或 -hard 工序编号）。

直接使用主 Agent 注入的已解析清单，无需自行解析。

### Step 1 — 全量阅读目标

用 Read 工具**全量**读取 `TARGETS` 中每个文件（长文件分段读完）；需要判定依据时读取 `BASELINE` 指向的基准文档。

### Step 2 — 按 MODE 执行

**`MODE=scan`（只读扫描）**：
1. 代码目标：按本文件 2.1 的四类规则与扫描要点逐项检查，逐条记录 `文件:行号 + 类别 + 问题描述 + 处置建议`。
2. 文档目标：按本文件 2.2 的八类规则逐项检查，逐条记录 `主题 + 各处原文位置与片段 + 建议修改方向`。
3. `-hard` 覆盖度审计任务（`BASELINE` 注入工序为 3.4 时）：按第三部分 3.4 的判定口径建立「交互规格 ↔ 测试」覆盖映射，输出未覆盖交互规格清单与冗余测试清单，逐条附依据（规格位置、对应测试或缺失说明）。
4. 只报告有把握的问题；存疑条目单独列出并说明不确定原因，不得无证据下结论。

**`MODE=hard-edit`（改写执行）**：
1. 按 prompt 六段中的「允许」与「严格禁止」清单，用 Edit 工具对 `TARGETS` 逐处修改；禁止脚本批量改写、禁止 git 写操作、禁止改动清单外文件。
2. 保持中文输出、原文笔调、完整句子、列表与标点风格。
3. 记录每处修改的前后对照；对放弃改动或有风险的位置单独列清单并说明原因。

### Step 3 — 输出完成信号

`MODE=scan`：

```
[LINT_DONE]
mode: scan
targets: [{file1}, {file2}, ...]
findings_code: {多余功能N, 旧代码N, 防御性N, 死代码N}
findings_doc: {矛盾N, 冗余N, 残留N, 过时表述N, 命令一致性N, 文档同步N, 设计一致性N, 中断残留N}
findings:
  - {文件:行号} | {类别} | {问题描述} | {处置建议}
uncertain:
  - {条目} | {不确定原因}
[/LINT_DONE]
```

`MODE=hard-edit`：

```
[LINT_DONE]
mode: hard-edit
targets: [{file1}, {file2}, ...]
lines: {before} -> {after}
edits: {修改处数}
samples:
  - 前: {原文片段}
    后: {改后片段}
skipped:
  - {位置} | {放弃/风险原因}
scope_confirmed: {已确认只改动注入文件清单: 是/否}
[/LINT_DONE]
```

然后**立即退出**，不得再调用任何工具。
