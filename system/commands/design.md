# ::design

> 命令索引见 `system/command_reference.md`。本文件为 `::design` 的完整执行协议。

## `::design`

总体设计命令。根据 `docs/requirements.md` 生成**或整体覆盖**两份全局设计文档：

- `docs/design.md`：**系统设计文档**——只写项目整体设计：架构形态与分层、核心架构决策与契约、模块清单、各模块的职责与边界（模块整体定义）、模块间行为与数据流。模块内部接口（函数签名、内部数据结构、子组件细节）一律不写，归 `docs/modules/{模块}_design.md` 与 `docs/modules/{模块}_interaction.md`。
- `docs/interaction.md`：**用户交互设计文档**——定义系统的全部交互行为：用户侧交互（CLI 逐命令、GUI 逐控件，含预期输入、预期输出、边界检查与错误处理）与模块间交互线协议（端点、帧格式、错误信封）。不与需求文档、设计文档重复内容。

两份文档的详细程度以下文「规格深度与裁剪规则」为准：**实现者不必猜测公共行为，测试者能写出明确断言**。

由主 Agent 直接执行。

**前置条件**：`docs/requirements.md` 存在且已被用户批准；不存在时提示先执行 `::req`。

**手动调用检查（门禁）**：本命令由用户手动调用时（非 loop 流程自然推进），先执行 `system/command_reference.md` 的「阶段门禁与手动调用提醒」：读 `status.md` 的 `[Current Phase]` 与 `[Phase History]`，向用户报告上一阶段完成情况与本次调用的性质（顺流程/回退重做/跨阶段跳转）；前置阶段未完成时提醒用户并等确认（全自动情景除外）。本次重设计构成打断时，必须执行下文「打断检测与归档」，禁止跳过归档直接覆盖。

**输入信息源**：
1. `docs/requirements.md`（权威需求来源）；
2. 二次开发场景：现有代码（设计须落到可复用资产上：哪些模块直接复用、哪些改造、哪些废弃）；
3. `qna/` 归档中的技术选型结论；
4. 已有 `docs/design.md` 与 `docs/interaction.md`（覆盖前读取）；
5. 打断续接场景：`docs/archive/` 中最近一次的中断归档（见「打断检测与归档」），新设计必须参考其中旧 dev 的执行进度。

**执行步骤**

**步骤 0 — 打断检测与归档**：读取 `status.md` 的 `[Current Phase]`。当本次重生成将改变整体设计、且 loop 已越过需求分析阶段时，先将旧版设计归档（归档协议见下文「打断检测与归档」一节）；仍处于 `需求分析` 阶段时不归档（与直接重做无区别，直接覆盖）。

**步骤 1 — 汇集信息源**：确定模块划分与核心抽象；存在中断归档时，先读 `interruption.md` 清单，确定哪些已完成模块直接复用、哪些半成品模块继续。

**步骤 2 — 撰写系统设计文档**：按「输出文档模板一」整体覆盖写入 `docs/design.md`，规格深度按「规格深度与裁剪规则」执行。

**步骤 3 — 撰写用户交互设计文档**：按「输出文档模板二」整体覆盖写入 `docs/interaction.md`。默认仅 CLI；仅当用户明确要求 GUI 时才包含 GUI 章节，且 GUI 一律按「GUI 套壳 CLI」的 WebUI 方式设计（GUI = CLI 的图形化适配层，每个 GUI 操作映射为一条 CLI 命令，禁止 GUI 绕过 CLI 直接操作业务层）。

**步骤 4 — 规格完整性与双向一致性检查**：对照下文「设计文档一致性检查」清单逐项核对两份文档，发现不一致先修复再展示；检查不通过时不进入报批与状态推进。

**步骤 5 — 等待用户批准**：向用户输出两份文档的要点（架构契约清单、模块划分与职责边界表、关键数据流、交互面总览（CLI 命令域清单、GUI 页面清单）、开发轮次规划、未决项清单），两份文档**均获批准**才算通过；用户提出修改时调整并重新覆盖、重新执行一致性检查，直到批准。（`/goal ::init` 等全自动情景下跳过批准等待，连续执行——**例外**：`status.md` 的 `[Repository State]` 为 `从零开始`（含无关的 loop中断恢复按从零处理）时不跳过，必须**逐文档**强制批准：`docs/design.md` 与 `docs/interaction.md` 各作为一项询问，使用 AskUserQuestion 或同类「询问-等待回答」交互工具取得明确批准；任一未批准时按用户说明修改对应文档、重新执行一致性检查后重新询问，直到两份均获批准；规范见 `system/command_reference.md`「从零开始强制批准门禁」。全自动不豁免规格完整性检查，未决项仍按「规格深度与裁剪规则」如实标注，不得写成确定事实。）

**步骤 6 — 更新状态**：`status.md` 的 `[Loop Cycle]` 写入/更新为 `第 N 轮 / 共 M 轮`（M 取本次设计的开发轮次规划；打断重设计时 N 递增）；两份设计文档获批准后，将 `[Current Phase]` 置为 `开发计划`，并向 `[Phase History]` 本轮行追加 `需求分析（{YYYY-MM-DD HH:MM}）`（需求分析阶段含 ::req 与 ::design，一并记录）；打断重设计时另起 `- 第 N 轮：` 新行。随后提示进入开发计划阶段（`::devplan`）。

## 打断检测与归档

loop 可以被需求变更打断。本命令是归档动作的执行点：当用户在 loop 进行中提出新需求、经 `::req` 更新需求文档后执行本命令重设计时，按以下规则归档旧版设计。

**触发判定**：`status.md` 的 `[Current Phase]` 为 `开发计划` / `模块开发` / `分支合并` / `代码检查` / `库级测试`，且已存在 `docs/design.md`，且新需求导致整体设计改变。`需求分析` 阶段被打断不归档（直接覆盖重做）。`::req` 在开发中后期不会提前改写阶段字段（见 `system/commands/req.md`），故本判定看到的是真实阶段。

**归档动作**（归档目录 `docs/archive/loop{N}-{YYYY-MM-DD}/`，N 为被打断的轮次）：

| 阶段 | 归档内容 |
| --- | --- |
| 开发计划 | `design.md`、`interaction.md`、`devplan.md`（`plans/current.md` 快照）、`interruption.md` |
| 模块开发 / 分支合并 / 代码检查 / 库级测试 | 同上；`interruption.md` 中必须含 dev 执行进度与残留文件清单（含未合并的 `dev/*` 分支与 `.worktrees/` 下 worktree 的清单及处置） |

`interruption.md`（中断清单）格式：

```markdown
# 中断记录 — loop{N} 于 {YYYY-MM-DD} 中断

- 中断时阶段：{开发计划/模块开发/分支合并/代码检查/库级测试}
- 中断原因：{新需求摘要}
- 中断时 devplan checklist 状态：
  - [x] {已完成模块}（可复用）
  - [~] {半成品模块}：{已完成的部分、剩余工作}
  - [ ] {未启动模块}
- 半成品说明：{每个半成品模块：已实现的接口/文件、未实现的部分、与代码现状的对应关系}
- 残留文件清单：{被打断的 dev 已创建、在新设计中可能不再被使用的文件列表；无则写「无」}
```

**归档后**：`status.md` 的 `[Loop Cycle]` 递增（如 `第 1 轮 / 共 2 轮` → `第 2 轮 / 共 M 轮`，M 按新设计重排）；`[Current Phase]` 回到 `需求分析` 后续阶段由流程自然推进。归档快照确认完整后才覆盖旧设计；归档失败时中止覆盖并向用户报告，不得宣告归档完成。

**新设计的承接要求**：重新生成的 `docs/design.md` 必须包含「承接被中断的上轮开发」一节，引用最近一次 `interruption.md`：已完成模块标记为直接复用、半成品模块写明从哪个状态继续、未启动模块并入新轮次规划、残留文件给出处置（删除/改造/保留）。`docs/interaction.md` 不再单设承接章节——交互侧的承接（哪些命令/页面保留、调整、废弃）体现在逐命令、逐控件规格的当前状态中。禁止无视旧 dev 进度从头设计。

## 规格深度与裁剪规则

两份设计文档的详细程度以「实现者不必猜测公共行为，测试者能写出明确断言」为准——不是行数或章节数量。每份文档只在**自己的职责范围**内追求完整：

| 文档 | 职责范围（完整覆盖的对象） |
| --- | --- |
| `docs/design.md` | 架构决策与契约、模块清单与各模块职责/边界、模块间行为与数据流、状态机、开发轮次规划 |
| `docs/interaction.md` | 全部用户交互（逐 CLI 命令、逐 GUI 控件）与模块间交互线协议——每个交互含预期输入、预期输出、边界检查、错误处理四要素 |

模块内部接口与实现细节的规格深度归 `docs/modules/{模块}_design.md` 与 `docs/modules/{模块}_interaction.md`（由 `::devplan` 建立、规范见 `system/commands/dev.md`「模块文档规范」），两份全局文档均不重复展开。

按三类裁剪：

| 类别 | 内容 | 要求 |
| --- | --- | --- |
| 必须完整 | 本轮需求涉及的架构契约、模块边界、用户入口、关键业务状态、交互规格、错误结果、验收条目 | 按模板逐字段写全 |
| 条件适用 | 配置覆盖链、并发、事务、重试、取消、持久化、实时通信等机制 | 项目实际涉及才展开；展开就写全 |
| 不适用 | 与项目无关的机制 | 保留章节标题并注明具体原因；禁止用「按需实现」「支持扩展」等表述代替规格 |

**规则**：

- **唯一定义归属**：每个架构契约、返回协议、错误分类、配置规则只在一个文档的一个章节权威定义，其他章节与其他文档引用；禁止两处分别维护同一字段表（全局交互协议——返回信封、错误分类、Exit Code——在 `docs/interaction.md`「全局交互协议」章定义，`docs/design.md` 只写决策）。
- **空值语义**：区分省略、`null`、空字符串、空集合；只有行为确实相同时才允许合并描述。
- **组合约束**：单字段约束与跨字段约束分开写；互斥、依赖、条件必填必须显式列出。
- **处理顺序**：关键流程写明校验、计算、写入、通知的先后顺序及失败点，不能只给数据流图。
- **未决项纪律**：每个未决项记录「未确定内容、影响范围、所需决策」；影响本轮公共契约或验收的未决项不得视为已通过；全自动情景跳过人工等待不等于允许把未知写成事实。
- **预期/实际分离**：设计文档只定义预期行为与验证方法；实际测试结果只由 `::dev` / `::ci` 写入 `docs/test.md`，设计文档不得写「已测试通过」。
- **示例纪律**：公共契约与交互规格至少覆盖最小成功案例与关键边界/失败案例；示例中的字段、类型、错误码必须与定义一致（示例与定义互相校验）。

## 设计文档一致性检查

每次生成或修改 `docs/design.md` 与 `docs/interaction.md` 后，必须逐项核对：

1. **命令域 ↔ 模块映射**：`interaction.md` 中每个 CLI 命令域都能落到 `design.md` 的某个模块，无孤儿命令域；
2. **能力覆盖**：`design.md` 中每个用户可见的功能在 `interaction.md` 中有对应交互入口（CLI 命令或 GUI 页面）；
3. **GUI → CLI 映射合法**（有 GUI 时）：GUI 章节只引用已定义的 CLI 命令；GUI 无任何绕过 CLI 的直接业务操作；
4. **需求落点**：`docs/requirements.md` 的每个核心需求与验收目标在 `design.md` 有设计落点、在 `interaction.md` 有交互落点（关联表可追）；无需求依据的新能力不出现在设计中；
5. **职责边界完整**：`design.md` 的每个模块均有职责、数据所有权与边界（不负责什么）的定义，模块清单与架构图一致；
6. **交互规格完整**：`interaction.md` 覆盖全部用户交互（每条 CLI 命令、每个 GUI 控件）与全部模块间交互线（端点/通道）；每个交互含预期输入、预期输出、边界检查、错误处理四要素，无「待补」占位；
7. **契约互一致**：`interaction.md` 引用的返回协议、错误分类、状态枚举与 `design.md` 的架构契约一致；同一概念在两份文档间无冲突定义（唯一定义归属），默认值与生效规则能推导出唯一结果；
8. **失败与边界有结果**：关键成功路径与实际相关的失败/边界情形均有明确的对外结果与副作用说明；
9. **验收可断言**：`design.md` 的架构验收标准与 `interaction.md` 的交互验收口径每条均含可观察断言，可逐条核验；
10. **未决与裁剪明确**：待确认项记录问题/影响/所需决策；跳过章节注明原因；无占位符冒充完成；
11. **可承接性**：两份文档足以供 `::devplan` 直接建立模块文档——模块职责边界与交互规格齐全，无需重新决定架构契约与交互形态。

## 贯通示例（协议演示）

> 本节是**写法演示**（虚构项目），展示「一个需求如何贯穿到验收断言」；不得将示例内容复制为目标项目的需求或设计。

**需求**（requirements.md）：FR-1 用户可以创建本地任务，任务含名称与优先级。

**架构契约**（design.md 核心架构决策与契约章）：全部控制操作经 CLI 暴露；CLI 提供 Human 与 `--json` 双模式；错误分类与退出码稳定（输入错误 2、状态错误 3——信封字段与分类表在 `docs/interaction.md` 定义，本章只写决策）。

**模块整体定义**（design.md 模块划分章）：`cli` 模块——职责：参数解析与输出格式化；边界：不含业务规则；`todo_store` 模块——职责：任务创建与持久化；数据所有权：`data/tasks.jsonl` 由其独占写入。两模块经直接调用协作，字段级接口规格见 `docs/modules/todo_store_interaction.md`。

**交互规格**（interaction.md CLI 命令域章）：

| 项目 | 内容 |
| --- | --- |
| 语法 | `todo add <name> [--priority low\|normal\|high]` |
| 参数与输入校验 | `name` 必填位置参数，1–100 字符；空字符串/全空白 → 解析层拦截（退出码 2，不写文件）；`--priority` 可选，缺省 `normal`，取值外 → 同上拦截 |
| 成功输出 | Human：`已创建任务 3fa9…：买牛奶（优先级 normal）`；Machine：`data` 含 `id`/`name`/`priority`/`created_at` 四字段 |
| 错误分类 | 名称非法 → `E_INVALID_NAME`（退出码 2）；存储目录未初始化 → `E_NOT_INITIALIZED`（退出码 3） |

**验收断言**（design.md 架构验收标准 / interaction.md 交互验收口径）：

- AC-1：合法调用后退出码 0；`data` 四字段齐全；`tasks.jsonl` 新增一行且 `priority` 为缺省 `normal`。
- AC-2：非法名称退出码 2；stderr 含 `E_INVALID_NAME`；`tasks.jsonl` 行数不变。

## 输出文档模板一：系统设计文档（`docs/design.md`，按项目类型裁剪，跳过的章节注明原因）

```markdown
# {项目名}

## 软件总体设计说明书

目标系统：{一句话}

# 1. 文档范围与分工
本文档描述项目整体设计：架构分层、核心架构决策与契约、模块清单、各模块的职责与边界、
模块间如何协作与数据如何流动。
本文档不写模块内部接口（函数签名、类成员、内部数据结构、子组件细节——
归 docs/modules/{模块}_design.md 与 {模块}_interaction.md），不逐条定义交互行为（归 docs/interaction.md）。
文档体系分工表：
| 文档 | 管辖范围 |
| docs/requirements.md | 需求：系统要做什么、架构选择（用户决策层）与性能约束、验收口径 |
| docs/design.md（本文档） | 整体设计：架构、契约、模块边界、模块间行为 |
| docs/interaction.md | 交互定义：全部用户交互（逐命令/逐控件）与模块间交互线协议 |
| docs/modules/{模块}_design.md | 模块内部设计：内部结构、内部数据流、内部数据结构、内部状态机 |
| docs/modules/{模块}_interaction.md | 模块逐接口交互规格（签名 + 输入/输出/边界检查/错误处理） |
| docs/test.md | 全局测试注册表：全部测试条目（分节）与最近一轮结果 |

# 2. 系统目标与核心抽象
系统目标一段话；核心业务能力清单；核心抽象（跨模块概念清单，逐名一行定义，非接口细节）；
需求—设计关联表：| 需求编号或章节 | 模块 | 用户入口（CLI 命令域/页面） | 验收条目 |

# 3. 总体架构
架构形态（进程与组件构成）；架构分层；总体结构图（ASCII）；
控制平面与数据平面的划分（如涉及实时数据通道）。

# 4. 核心架构决策与契约
架构级契约逐条列出（任何模块改动不得破坏），按项目实际裁剪，典型条目：
- 控制接口形态（如「CLI 为唯一控制接口，GUI 套壳 CLI」）；
- 返回协议与错误模型决策（统一信封、错误分类——字段与取值表以 docs/interaction.md
  「全局交互协议」章为唯一定义，本章只写决策）；
- 插件机制与注册表（如涉及）；
- 数据链与时间口径（如涉及录制、多时钟域）；
- 幂等与停止链契约、状态机契约；
- 数据隔离（哪些目录不入库）；
- 模块协作机制（Direct Interface / Port·Protocol / Event 的适用规则）；
- 全局约定：时间格式、标识规则、空值语义、配置来源与覆盖规则（实际涉及才展开）。

# 5. 模块划分与职责边界
模块的正式定义：围绕一项稳定业务能力组织的一组代码、数据模型、状态和接口——
模块拥有明确的内部职责和公共边界，并能通过稳定接口与其他模块协作；
判定条件：业务职责 / 数据所有权 / 公共接口 / 内部封装 / 可独立测试。
第一层模块清单；模块 ↔ 用户入口映射表（CLI 命令域/页面 → 承载模块）；
各模块整体定义（每模块一小节）：职责（一句话业务闭环）、数据所有权、
边界（明确不负责什么）、详见 docs/modules/{模块}_design.md 与 {模块}_interaction.md；
源码布局（目录树）。

# 6. 模块间行为与数据流
模块依赖方向图；主要数据链逐条描述（起点 → 途经模块 → 终点，各环节职责与协作机制）；
跨模块数据一律以明确 DTO 流动（本章只列 DTO 清单，
字段级定义归拥有方模块的 docs/modules/{模块}_design.md）。

# 7. 生命周期与状态机
各业务对象状态机（跨模块行为契约）；状态可观察性（状态查询入口）。

# 8. 并发模型与时间模型（条件适用）
进程/线程/事件循环模型；时间域分离与换算边界。项目不涉及则注明原因。

# 9. 开发轮次规划
本项目整体设计需要 N 个完整 loop 循环（::req → ::design → ::devplan → ::dev → ::lint → ::ci）：
每轮一节——轮次目标、功能范围（最小完整链路优先）、交付物。当前文档对应第几轮。
（打断重设计时本节重排剩余轮次。）

# 10. 承接被中断的上轮开发（仅打断续接场景保留；首轮设计省略本章）
引用 docs/archive/loop{N}-{日期}/interruption.md：已完成模块（直接复用）/
半成品模块（从何状态继续）/ 未启动模块（并入轮次规划）/ 残留文件处置。

# 11. 测试架构概览
测试分层（单元/契约/集成/端到端/性能等，按项目裁剪）；模块测试责任映射；
全部测试依据交互文档设计（docs/interaction.md 与模块交互文档），
逐条注册于 docs/test.md（注册格式与结果记录见 system/commands/dev.md「测试文档规范」）。
（本章只定义预期行为与验证方法；实际测试结果只写入 docs/test.md。）

# 12. 架构验收标准
架构层面验收项编号清单（每条关联需求/契约，可逐条验证）。
```

写作要求：
- 只写整体设计：架构、契约、模块边界、模块间行为。模块内部接口与实现细节一律不写，指向 `docs/modules/{模块}_design.md` 与 `{模块}_interaction.md`；交互行为的逐条定义不写，指向 `docs/interaction.md`。

- 推荐源码结构以目录树形式给出。
- 规格深度按「规格深度与裁剪规则」执行；严禁编造与需求无关的设计；未确定的技术选型按未决项纪律标注「待确认（未确定内容 / 影响范围 / 所需决策）」并向用户提出。
- 示例中的字段、类型、错误码必须与定义一致。

## 输出文档模板二：用户交互设计文档（`docs/interaction.md`，按项目类型裁剪，跳过的章节注明原因）

```markdown
# {项目名}

## 用户交互设计说明书

交互方式：CLI（默认）{；含 GUI（Web）——仅当用户明确要求}

# 1. 文档定位与边界
本文档只回答四类问题：①用户与外部系统能与系统发生哪些交互；②每个交互的预期输入是什么、
系统如何校验；③预期输出是什么、以什么形式呈现；④输入非法或对端失败时，交互双方各自看到什么。
不写需求罗列（归 docs/requirements.md），不写模块划分与模块内部设计
（归 docs/design.md 与 docs/modules/）。涉及模块边界时只写到「交互线协议」层：
请求/响应的字段、帧格式、错误信封——两个模块在交互点上互相承诺什么，
不解释模块内部如何兑现。

# 2. 交互面总览
交互通道清单表：| 通道 | 形态 | 承载内容 | 协议约定 |；
各类使用者与通道的等价关系；入口清单（CLI 命令域总清单、GUI 页面清单——如有）；
交互架构图（ASCII）。

# 3. 全局交互协议
全部交互共用的约定（后续章节不再重复）：
- CLI 调用形式与输出模式（Human / Machine（--json））；
- 统一返回协议（信封字段定义）与 Exit Code 分类表——本章唯一定义，
  各命令只写自己的 data 业务结构与 error 取值；
- 各通道的错误呈现形态（CLI stderr / GUI 提示 / HTTP 错误体等，按项目实际）；
- 通用交互行为（防连点、破坏性操作二次确认、断线重连、轮询兜底等，按项目实际裁剪）；
- 状态驱动可用性规则（控件「状态 → 可用性」表，如项目有 GUI/状态机）。

# 4. ~ N. CLI 逐命令交互规格
每个命令域一节；每条命令一份交互规格：
- 完整语法（位置参数、选项、互斥与依赖）；
- 参数与输入校验：| 参数 | 类型 | 必填 | 默认值 | 取值/范围 | 非法输入的拦截点与表现 |；
- 成功输出：Human 形态要点 + Machine data 结构要点（引用全局信封，不重复定义）；
- 错误分类：各错误码/退出码的触发条件与表现；
- 适用时的空结果、幂等、取消与超时行为。

# N+1. 模块间交互线协议
模块间每一条交互线的输入/输出/错误形态，逐线定义：
- 服务端点或进程间通道（如 HTTP / WebSocket / 队列）：参数、成功输出字段、失败形态；
- 实时通道逐主题帧协议：帧布局、字段含义、边界处理（坏帧/乱序/断线）、首帧与增量语义；
- 事件总线（如适用）：事件类型清单与载荷字段。
（进程内直接调用的字段级契约归被调方模块的 docs/modules/{模块}_interaction.md，本章不重复；
无此类交互的项目注明原因并省略本章。）

# N+2. GUI 页面逐控件交互规格（仅当用户明确要求 GUI；否则本章只写
「本项目不提供 GUI，全部交互经 CLI 完成」）
每个页面一节：页面初始化行为序列（加载时执行的请求/连接）；区域划分；逐控件规格表：
| 控件 | 触发（端点/通道/纯前端） | 期望输入 | 成功时的界面表现 | 非法输入/后端失败时的界面表现 |
控件可用性引用「全局交互协议」章的状态驱动规则表，不逐控件重复。
GUI 一律按「GUI 套壳 CLI」设计：每个 GUI 控制操作映射为一条 CLI 命令，
禁止 GUI 绕过 CLI 直接操作业务层；同表给出 | GUI 操作 | CLI 命令 | 映射总表。

# N+3. 端到端交互序列
典型用户流程：用户动作与系统反馈的序列（CLI 命令链逐步列出；
GUI 场景给出等价操作链，二者业务结果一致）。

# N+4. 交互验收口径
编号清单，每条可由「交互行为是否如本文档所述」直接核验（含可观察断言），至少覆盖：
每条核心控制行为有 CLI 命令；CLI 可独立完成完整业务流程；
GUI 核心操作全部映射到 CLI 命令且业务结果一致（如有 GUI）；CLI 提供 Human 与 JSON 两种输出。
```

写作要求：
- 只写交互：用户交互（逐命令、逐控件）与模块间交互线协议；模块内部实现引用 `docs/design.md` 与 `docs/modules/`，不重复展开。
- 每个交互行为必须含四要素：预期输入（含校验与边界检查）、预期输出（呈现形式）、非法输入表现、对端失败表现。
- 不与 `docs/requirements.md`、`docs/design.md` 重复内容：需求理由、架构论证、模块内部设计一律引用而非复述；全局交互协议（信封/错误分类/Exit Code）在本文件「全局交互协议」章唯一定义一次，`docs/design.md` 只写决策。
- 严禁编造需求之外的交互方式；用户未要求 GUI 时不得设计 GUI。
- 规格深度按「规格深度与裁剪规则」执行。
