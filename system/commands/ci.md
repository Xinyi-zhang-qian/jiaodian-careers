# ::ci

> 命令索引见 `system/command_reference.md`。本文件为 `::ci` 的完整执行协议。

---

## `::ci` / `::ci test`

库级测试命令。负责库级（模块间级与整库级）测试的编写、修改与执行，通过后更新所有文档。由主 Agent 直接执行。

**参数格式**：
- `::ci`：完整流程——编写/修改库级测试 → 执行 → 通过后更新所有文档。
- `::ci test`：子操作，**只运行测试**（不编写新测试、不更新文档），输出测试报告。

**前置条件**：`::dev` 全部模块完成且 `::mergelocal` 已把全部 `dev/*` 分支合并回主工作区（`plans/current.md` checklist 仅剩最后的整合测试项，`local.md` 的 worktree 清单已清空）。

**执行步骤（`::ci` 完整流程）**

**步骤 1 — 测试设计**：对照 `docs/design.md` 的测试架构与 `plans/current.md` 的整合测试项，确定库级测试清单：
- 模块间集成测试（跨模块数据流上的关键链路）；
- 端到端测试（用户接口层发起的最小完整链路）；
- 契约测试（插件/Port 接口的统一契约，如适用）；
- GUI 视觉验收（条件启用，见步骤 4）：启用时一并设计页面截图清单与交互流程镜头清单。

库级测试同样依据交互文档设计（规范见 `system/commands/dev.md`「测试文档规范」），确定后登记到 `docs/test.md` 的「全局测试」节。

**步骤 2 — 编写/修改测试**：实现上述测试（每条测试先登记 `docs/test.md` 再写测试代码）；已存在的库级测试按本轮变更修改。视觉验收启用时，一并实现/更新截图工具脚本与机器门控测试（见步骤 4）。

**步骤 3 — 执行测试（严格按 test.md 全图回归）**：以 `docs/test.md` 登记的全部条目为唯一回归清单——按「全局测试 → 各模块分节」逐条执行各条目登记的「如何运行」，不得自行增删、不得只跑最近改动的部分。`::dev` 阶段只运行了本轮修改模块的测试，本步骤是本轮首次全量回归。
- 执行中发现登记与实际不一致（条目无对应测试、「如何运行」不可执行、存在未登记的实际测试）→ 停下修正：属登记偏差的按「不一致采纳优先级」修正 `docs/test.md` 后重跑该条；属测试缺失的回到步骤 2 补写后重跑；属测试失败的按下述失败流程处理；
- 全部通过 → 步骤 4；
- 有失败 → 定位责任模块，修复后重跑；需要改接口设计时停下并向用户报告（必要时回到 `::devplan`）。

**步骤 4 — GUI 视觉验收（条件启用）**：

**启用判定**——以下三个条件同时满足才启用，任一不满足则 skip：

1. 任务要求 GUI：`docs/interaction.md` 含 GUI 章节（用户要求 GUI，按「GUI 套壳 CLI」模式设计）；
2. 当前执行模型具备视觉能力（可 Read PNG 截图并判读内容）；
3. 本机可探测到浏览器后端（chrome / chromium / headless-shell 等）。

skip 不算失败：在 `::ci` 结果与 `system_log.md` 中**如实记录 skip 原因**（无 GUI / 模型无视觉能力 / 无浏览器后端），**禁止以 mock 或凭空构造的图像冒充真实截图**。

**设计要点**（首次启用时建立，后续轮次复用）：
- **截图/场景驱动脚本**（建议 `scripts/` 下独立脚本）：页面清单逐页截图（覆盖 `docs/interaction.md` 的全部 GUI 页面）+ 关键交互流程镜头（沿状态机转换：初始态 → 操作 → 状态变化逐镜头截取）；
- **确定性截图**：固定视口并隐藏滚动条；等待页面就绪（`document.readyState` 轮询）；对异步操作结果用**条件轮询**等待真实结果出现（如目标表格行出现），禁止只靠固定 sleep 猜时机；
- **控制台错误采集**：截图时同步采集浏览器控制台 JS 错误（异常 / error 级日志 / console.error）；
- **manifest.json**：每次运行落盘——`generated_at`（时区化时间戳）、`base_url`、`browser`、`viewport`、`pages[]`/`flow[]`（name/file/ok/bytes/console_errors/stats），作为机器断言数据源、模型判读复核依据与产物新鲜度判定依据；
- **机器门控**（纳入库级测试）：截图文件存在且大于最小字节数；非空白像素/颜色多样性阈值（以颜色多样性为主，如 `distinct_colors ≥ 8`——深色场景非白占比恒高，单看非白占比会误判）；控制台 JS 错误为 0；
- **作用对象**：真实运行的应用（真实服务进程/Runtime，可用 Fake 数据源兜底），不用进程内 Fake 冒充渲染层。

**执行流程**：
1. 启动应用至**初始态**（流程镜头要求无遗留的运行中状态）；
2. 运行截图脚本，产物落 `workspace/gui_visual/`（PNG + `manifest.json`）；
3. 主 Agent **逐张 Read 全部 PNG**，以 manifest 为复核索引，按 rubric 六项判读：
   1. 布局结构完整（各区/导航/折叠区就位）；
   2. 关键区域非空白且有真实内容；
   3. 状态徽标与按钮可用性符合状态机（禁用须带原因提示）；
   4. 空态引导清晰（缺什么前置、去哪里操作）；
   5. 无裁切 / 重叠 / 异常空白；
   6. 控制台无 JS 错误（以 manifest `console_errors` 为准）。
4. 写 `workspace/gui_visual/verdict.json`：`generated_at`、`manifest_generated_at`（必须与最新 manifest 同批）、`rubric`、`overall`（pass/fail）、`warn_items[]`、`items[]`（逐项：`page` / `check` / `verdict`(pass|warn|fail) / `evidence` / `note`）。**防幻觉要求**：逐项给出截图内可见证据；不确定的判定记 warn 并在 note 说明原因，不得无证据下结论；
5. 门控判定：机器门控全部通过且 verdict `overall == "pass"`、items 无 fail → 通过；否则进入修复循环。

**修复循环**：门控或判读出现问题时，**直接定位并修复**（前端资源或服务端渲染），修复后**强制重拍并重判**（前端静态资源改动后必须重新截图，否则 manifest 新鲜度/同批校验失败），重复直到全部通过为止。

**产物入库策略**：`workspace/gui_visual/*.png` 不入库（加入 `.gitignore`，体积大、可重跑再生）；`manifest.json` 与 `verdict.json` 为文本产物，入库供测试门禁与历史比对。

**步骤 5 — 更新所有文档**：
- `docs/test.md`：更新「最近一轮结果」（整库：日期、通过/失败统计、失败明细与处置；视觉验收启用时含页面/镜头数、verdict 结论与 warn 项，skip 时含原因）；
- `plans/current.md`：勾选最后的整合测试项；
- `docs/requirements.md`：逐条核对验收目标，更新完成状态；
- `docs/design.md` 与 `docs/interaction.md`：与最终实现同步（两份文档改动后按 `system/commands/design.md` 的「设计文档一致性检查」核对一致性）；同步中遇到文档与代码不一致时，按 `system/command_reference.md`「不一致采纳优先级」确定权威方并修正另一方（需要改代码时向用户报告偏差后再修复）；
- `README.md`：运行方式/功能变化时按 `system/commands/dev.md` 的「README 维护规范」更新；
- `status.md`：`[Current Phase]` 置为 `已完成`，并向 `[Phase History]` 本轮行追加 `库级测试（{YYYY-MM-DD HH:MM}）`。

**步骤 6 — 汇总**：向用户输出测试报告（分层 × 通过/失败统计；视觉验收启用时含页面/镜头数、verdict 结论与 warn 项，skip 时含原因）与文档更新清单；本轮 loop 完成——若设计文档「开发轮次规划」仍有后续轮次（`[Loop Cycle]` 的 N < M），提示用户以 `::req` 启动下一轮循环。

**`::ci test` 子操作**：只执行步骤 3 的运行部分（回归清单同样严格以 `docs/test.md` 登记条目为准；视觉验收的机器门控用例随整库回归一并运行，不重新截图与判读），输出测试报告后结束，不修改任何文档。

**`docs/test.md` 维护说明**：全局测试文档的结构与登记格式（全局测试 / 模块分节、逐条 {测试名称 / 如何运行 / 测试内容}、「最近一轮结果」节）以 `system/commands/dev.md`「测试文档规范」为权威；本命令负责登记库级测试条目并更新整库结果。

## 运行日志

本命令执行完毕后，必须向仓库根目录 `system_log.md` 追加一条记录：

````markdown
## [YYYY-MM-DD HH:MM:SS] {命令原文}
- 库级测试 {通过N/共M} | 视觉验收: {通过（页面N+镜头M）/skip（原因）/未启用} | docs/test.md 已更新 | 阶段: 已完成
````

`::ci test` 子操作时摘要为 `- 测试运行 {通过N/共M}（仅运行）`。
