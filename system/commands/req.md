# ::req

> 命令索引见 `system/command_reference.md`。本文件为 `::req` 的完整执行协议。

---

## `::req [补充需求]`

需求分析命令。根据用户输入（`::init` 的 custom prompt 或本命令的补充需求）生成**或整体覆盖** `docs/requirements.md`。由主 Agent 直接执行。

需求文档的**内容边界**（本命令的核心纪律）：需求文档只收录三类内容——

1. 用户侧提出的具体功能需求（系统要做什么、用户可见的期望行为与边界）；
2. 架构选择（用户决策层）：用户提出或经用户确认的平台级架构决策，属需求约束，改动须用户确认；
3. 用户明确提出的性能等约束（量化指标、规模目标、护栏条件）。

**禁止写入**任何设计内容：API 设计、接口签名、模块划分与模块内部设计、数据结构设计、错误码设计——这些归 `docs/design.md`、`docs/interaction.md` 与 `docs/modules/`。语言简洁清晰，遵循 `AGENTS.md`「全局语言风格」节。

本命令是阶段门禁的**豁免命令**：可随时手动调用（补充需求、开启新一轮 loop 均从本命令进入），不做「阶段门禁与手动调用提醒」。

**参数格式**（由主 Agent 使用 LLM 能力直接解析）：
- `[补充需求]`：可选。用户的新需求、修改意见或补充说明原文。缺省时以 `status.md` 的 `[Project Goal]` 与最近对话中的需求描述为输入。

**输入信息源**（按优先级）：
1. 本次命令的补充需求原文；
2. `::init` 的 custom prompt 与 `status.md` 的 `[Project Goal]`；
3. `qna/` 最近归档中的需求相关结论；
4. 二次开发场景：现有代码本身（`::init` 二次开发分支已通过 `::work -explore` 基于代码生成初版文档，本命令在其基础上与用户迭代）；
5. 已有 `docs/requirements.md`（覆盖前读取，保留仍然有效的需求）。

**执行步骤**

1. 汇集上述信息源，梳理需求清单。
2. 按下方「输出文档模板」撰写需求文档，**整体覆盖写入** `docs/requirements.md`（不续写、不追加；旧内容无需保留——历史版本由 git 管理）。
3. 更新 `status.md`：`[Current Phase]` 当前为 `需求分析` / `已完成` / 「（暂未设置）」时置为 `需求分析`；当前为 `开发计划` / `模块开发` / `分支合并` / `代码检查` / `库级测试` 时**保持原阶段不改写**——开发中变更需求的打断归档由后续 `::design` 依据真实阶段判定（见 `system/commands/design.md`「打断检测与归档」）。
4. 向用户输出需求文档的要点（总体功能划分、架构选择清单、验收目标），**询问用户是否批准进入设计/开发阶段**；用户给出更多需求时，将新需求作为输入重复本命令（直接覆盖重生成），直到用户批准。**从零开始强制批准门禁**：`status.md` 的 `[Repository State]` 为 `从零开始`（含无关的 loop中断恢复按从零处理）时，本门禁在任何情景（含 `/goal ::init` 全自动）都不得跳过——必须使用 AskUserQuestion 或同类「询问-等待回答」交互工具取得用户对 `docs/requirements.md` 的明确批准；未批准时按用户说明修改文档后重新询问，直到批准（规范见 `system/command_reference.md`「从零开始强制批准门禁」）。
5. 用户批准后：若 `docs/design.md` 尚不存在或与需求不同步，提示/继续执行 `::design`。

**输出文档模板**（`docs/requirements.md`，按项目类型裁剪，跳过的章节注明原因）：

```markdown
# {项目名}

## 软件需求规格说明书

目标系统：{一句话}
目标运行平台：{平台}
主要使用方式：{使用方式}

# 1. 文档目的与系统目标
本文档定义……系统的软件需求。系统需要提供的能力清单（逐条列出）；系统长期目标。

# 2. 产品定位
系统定位；围绕哪些核心业务对象组织（逐一定义）。

# 3. 用户角色
逐角色：职责、系统向其提供的能力、交互方式。
（运行环境也视为外部参与者：系统需要识别运行环境中的哪些要素。）

# 4. 总体功能划分
系统主要功能划分清单。

# 5. 架构选择（用户决策层）
用户明确的平台级架构决策，逐条编号（属需求约束，改动须用户确认）。
只收录用户提出或经用户确认的架构选择；设计层自行决策的架构细节不写入本章。
无此类决策时注明「无」。

# 6. 系统运行需求
支持平台、启动方式、运行状态检查。

# 7. ~ N-2. 分项功能需求
每个功能领域一节：用户可见的行为、数据内容、边界、典型配置。

# N-1. 性能需求
用户明确提出的性能约束（量化指标、规模目标、护栏条件）。

# N. 可扩展性、可维护性与可测试性需求
用户明确提出的扩展机制（插件/适配器等）与可维护性、可测试性要求。

# N+1. 验收目标
系统满足哪些条件时核心能力成立（编号清单，可逐条验证）。
```

写作要求：
- 内容边界见本文件开头「内容边界」节：只写用户侧需求、架构选择（用户决策层）与性能等约束；严禁写入设计与接口内容。
- 全部使用中文，语言简洁清晰；技术名词、字段名保留原文。
- 需求必须可验证（每条需求能对应到验收目标或测试）。
- 严禁编造用户未表达的需求；信息不足时向用户提问而非假设。
