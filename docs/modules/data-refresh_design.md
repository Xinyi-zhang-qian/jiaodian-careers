# data-refresh 模块设计文档

> 全局契约引用 docs/design.md §4（契约 17–19）、§5；本模块为第 2 轮执行模块（无新增源码，执行 + 少量批次修改）。

# 1. 模块职责与边界

- 职责：按 source-tools 的产出对前台数据执行三轮处置——①信息充实：对现行有效且字段空白的记录做字段提取确认与升级（目标 ≥60 条）；②失效刷新：对内容失配/来源过期记录重新检索现行来源（单位官网、政府人事部门网站的现行公告），检索到即刷新记录（更新 source_url/source_title/source_evidence 与字段，层级按新证据定）；③清理：确认无现行来源的删除，截止已过仍标「招聘中」的状态修正。全部处置留痕。
- 数据所有权：本轮对既有批次文件的修改（充实字段、刷新来源、删除记录、状态修正）与新增处置注释。
- 不负责：修改管线脚本（source-tools 所有）、页面代码（jobs-catalog）、新岗位批次（data-acquisition）。
- 执行路径说明（2026-11-05 第 2 轮）：第 2 轮处置以一次性脚本等价执行（复用 recheck-core 基建，脚本提交前删除）；第 2 轮之后同流程由 source-tools 的 extract:fields 与 refresh:sources 命令承载。脚本与分类明细均为一次性工作产物（workspace/source-refresh/，不入库）。

# 2. 内部结构（执行流程，无新源码）

```text
全量分类（188 条在线访问来源页）→ 处置队列分三类：
  A 现行有效且字段空白 → 逐条提取来源页载明的字段 → 批量写入批次文件并升级层级（充实 108 条（权威口径：leads 27 + restored 81，经 git 历史逐字段比对核实）。充实优先级：事业单位与科研院所记录优先（用户关注重点），其次企业，再次其他；同级按记录 id 顺序。删除记录必须在批次头注释记录处置（id、岗位、单位、原因、日期），与第 1 轮处置记录格式一致。

第 2 轮分类结果（2026-11-05）：现行有效 105、内容失配 81、访问失败 2（485 反爬拦截、209 超时，随 B 类处置）。分类口径：现行有效＝页面 2xx 且 source_title 与全部证据片段规范化后逐字命中；内容失配＝页面存在但锚点不命中、停招字样、过期提示页、JS 渲染壳（正文无岗位内容）、疑似失效跳转；来源过期＝404/410、域名失效；网络异常记「访问失败」人工复核。

已识别的工具链限制（写入处置规则）：GBK/GB2312 编码站点（qgsydw.com、zgsydw.com 等）经 audit-verified-jobs.ts 的 `response.text()`（按 UTF-8 解码）无法逐字命中中文证据——此类来源的记录层级不得高于「关键字段核验」（第 2 轮涉及 401–403、476、439）。页面正文为 JS 渲染壳（zhiye.com/feishu.cn 校招详情等）时同理不可升级；重新检索无现行可核验来源的按失效删除。
