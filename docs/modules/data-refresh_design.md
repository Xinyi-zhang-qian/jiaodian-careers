# data-refresh 模块设计文档

> 全局契约引用 docs/design.md §4（契约 17–19）、§5；本模块为第 2 轮执行模块（无新增源码，执行 + 少量批次修改）。

# 1. 模块职责与边界

- 职责：按 source-tools 的产出对前台数据执行三轮处置——①信息充实：对现行有效且字段空白的记录做字段提取确认与升级（目标 ≥60 条）；②失效刷新：对内容失配/来源过期记录重新检索现行来源（单位官网、政府人事部门网站的现行公告），检索到即刷新记录（更新 source_url/source_title/source_evidence 与字段，层级按新证据定）；③清理：确认无现行来源的删除，截止已过仍标「招聘中」的状态修正。全部处置留痕。
- 数据所有权：本轮对既有批次文件的修改（充实字段、刷新来源、删除记录、状态修正）与新增处置注释。
- 不负责：修改管线脚本（source-tools 所有）、页面代码（jobs-catalog）、新岗位批次（data-acquisition）。

# 2. 内部结构（执行流程，无新源码）

```text
refresh:sources 全量分类 → 处置队列分三类：
  A 现行有效且字段空白 → extract:fields --scan → 人工/AI 确认 → --apply 写库（充实，≥60 条）
  B 内容失配/来源过期   → 重新检索现行来源 → 检索到：刷新记录（批次内更新）→ 审计
                        → 检索不到：从批次删除 → 批次头注释处置记录
  C 状态矛盾（截止已过仍招聘中）→ 状态改「已截止」或随 B 删除
```

# 3. 内部数据流

处置顺序固定：先分类（refresh:sources）→ A 类充实（extract:fields scan/apply 循环，分批执行）→ B 类刷新或删除 → C 类状态修正 → `audit:jobs:offline` → 在线审计确认全量通过。充实优先级：事业单位与科研院所记录优先（用户关注重点），其次企业，再次其他；同级按记录 id 顺序。删除记录必须在批次头注释记录处置（id、岗位、单位、原因、日期），与第 1 轮处置记录格式一致。

# 4. 内部数据结构

无新增数据结构；充实与刷新作用于既有 `Job` 字段（含 `application_opens_at`、`job_functions`、`recruit_type`）。
