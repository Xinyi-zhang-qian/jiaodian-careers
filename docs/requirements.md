# 交点 Careers（jiaodian-careers）

## 软件需求规格说明书

> 版本：V4.0（第 3 轮需求分析，`::req` 生成）
> 输入：用户本轮设想原文（见文末附录）+ 第 2 轮已交付系统现状（216 条岗位、12 批次）
> 内容边界：本文档只收录用户侧功能需求、架构选择（用户决策层）与性能等约束；设计内容归 docs/design.md 与 docs/interaction.md。

目标系统：面向人文、社会科学与理工科交叉人才的招聘信息静态网站。
目标运行平台：Web 浏览器（静态托管，部署于 Render）；数据维护在本地 Node.js 环境完成。
主要使用方式：求职者用浏览器浏览、筛选、收藏、获得个性化岗位推荐；内容维护者通过命令行脚本与规范化数据文件增补、核验、构建与部署。

# 1. 文档目的与系统目标

本文档定义交点 Careers 的软件需求。系统既有能力清单（第 1、2 轮已交付，保持）：

1. 经来源核验的岗位目录（216 条、12 批次），筛选、排序、分页、URL 复现、本地收藏。
2. 岗位详情溯源展示（核验锚点、报名窗口、即将截止/报名已截止标识、来源链接）。
3. 规范化数据源、增补与审计管线、字段提取辅助与来源刷新工具。
4. 交叉方向浏览、实习/分析/市场内容页。
5. 静态导出与 Render 自动部署。

**本轮（第 3 轮）新增目标**：

6. **岗位匹配推荐**：用户输入自己的教育经历（不同阶段的专业）、工作经历（岗位名称）、技能特长，系统据此筛选并推荐匹配的岗位。
7. **画像条目动态管理**：用户可以通过「添加」增加专业或工作经验等条目，也可删除；画像保存在用户浏览器本地。
8. **详情页信息充实**：每个招聘信息的详情页展示更完整的信息——记录拥有的字段全量展示、长文本完整渲染，并对仍缺字段的记录补充提取。

系统长期目标不变：成为交叉背景求职者可信赖的信息入口——宁可少展示，不可展示未经核验或编造的内容。

# 2. 产品定位

系统定位：招聘信息聚合与核验展示站点，不做简历投递、不代理招聘流程，只提供经核验的信息与原始来源链接。本轮新增的匹配推荐是**参考性排序**，基于平台标签与已核验字段，不构成录用资格判断。

核心业务对象（新增）：

- **用户画像（Profile）**：求职者在本机保存的自我描述——教育经历（阶段+专业）、工作经历（岗位名称）、技能特长三类条目，每类可动态增删。
- **匹配结果（MatchResult）**：画像与岗位的匹配评分与理由（哪条条目匹配了岗位的哪个信息）。

# 3. 用户角色

- **求职者（浏览器访客）**：填写/维护自己的画像，查看匹配推荐岗位列表及推荐理由，继续使用既有浏览/筛选/收藏能力。
- **内容维护者**：为详情页充实执行补充提取与审计。
- **运行环境参与者**：Render 构建流水线；来源网站（补充提取的访问对象）。

# 4. 总体功能划分

既有功能（保持）：岗位目录与筛选、岗位详情、首页、交叉方向、收藏、实习/分析/市场内容页、核验管线、数据工具、静态部署。

本轮新增/强化：

9. 用户画像管理（页面 /match，画像条目动态增删、本地保存）
10. 岗位匹配推荐（画像驱动打分排序与匹配理由）
11. 详情页信息充实（全量字段展示 + 长文本完整渲染）
12. 稀疏记录补充提取（对仍无条件字段的记录用 extract:fields 补齐）

# 5. 架构选择（用户决策层）

既有决策全部保持：纯静态站点、数据文件化、三级核验层级、Render 部署、推送统一经 `::push`。

本轮新增决策（待用户确认）：

7. **画像与匹配全部在浏览器本地完成**：画像存 localStorage（与收藏同机制），匹配计算在浏览器内存中对 jobsCatalog 执行；不新增后端服务、不上传任何用户数据（与纯静态架构一致）。
8. **匹配依据限定为已核验信息**：打分只使用岗位的平台标签（方向/职能/技能）与已核验字段（专业要求原文、标题），不使用推测内容；推荐结果必须展示匹配理由供用户自行判断。

# 6. 系统运行需求

- 既有命令保持；本轮新增的补充提取使用既有 `extract:fields` 工具（无新命令）。
- 构建护栏：新增匹配页面为纯客户端渲染，不增加构建期负担。

# 7. 用户画像管理（/match，本轮新增）

- 用户可见行为：
  - 三组条目，每组可「添加」多条、可单条删除：**教育经历**（阶段 + 专业名称，阶段可选本科/硕士/博士，并支持自定义输入阶段名称）、**工作经历**（岗位名称）、**技能特长**（名称）。
  - 画像自动保存在浏览器 localStorage；再次访问自动恢复；可一键清空。
  - 输入即计算：条目变化后推荐结果实时更新。
- 边界：无账号体系；换浏览器不同步；不采集也不上传任何画像数据。

# 8. 岗位匹配推荐（本轮新增）

- 用户可见行为：按当前画像对全部前台岗位打分排序，展示推荐岗位列表（复用 JobCard 形态），每条推荐附**匹配理由**（例如：「硕士专业『计算语言学』匹配岗位专业要求原文」「技能『Python』匹配岗位技能标签」）；无画像或画像为空时给出引导文案。
- 数据内容：打分依据为岗位的方向标签、职能标签、技能标签、标题与专业要求原文（全部为已核验或平台标注信息）。
- 边界：推荐不改变岗位既有数据语义；匹配结果页可与地区、单位类型等筛选组合；推荐不构成录用资格保证。

# 9. 详情页信息充实（本轮新增）

- 用户可见行为：详情页完整展示记录拥有的全部信息——原公告资格条件、学历/经验、薪资、职责、优先条件、招聘人数与报名安排、联系方式、本站说明等区块按实际字段渲染，长文本完整显示不截断；对已有信息不再出现「有数据但未展示」的区块。
- 边界：只展示已核验/已提取字段，展示口径仍受核验层级约束；不因充实而改变数据语义。

# 10. 稀疏记录补充提取（本轮新增）

- 数据内容：对仍无条件字段的记录（现状 9 条）与关键字段核验记录中可补的，使用既有 `extract:fields` 工具做一轮补充提取（人工确认后入库），缩小详情页信息差距。
- 边界：与第 2 轮充实同规则——证据可回溯、核对不到留空、不推测补写。

# 11. 性能需求

- 用户未提出量化指标。新增约束（护栏）：匹配计算在浏览器本地进行，200+ 条目录的打分应即时完成（无感知延迟）；画像条目数量无硬限制。

# 12. 可扩展性、可维护性与可测试性需求

- 匹配算法集中实现（便于后续调优权重与扩展画像维度）。
- 测试：匹配算法与画像管理的模块测试、详情页展示断言、整库回归按既有体系扩展。

# 13. 验收目标

1. `/match` 页可添加、删除三类画像条目（教育经历含自定义阶段），画像经刷新后保持，可一键清空。
2. 填写画像后，推荐列表按匹配度排序且每条推荐带可读的匹配理由；清空画像后回引导态。
3. 匹配打分只使用平台标签与已核验字段；推荐结果与手动筛选结果对同一岗位的信息一致。
4. 详情页对记录拥有的字段全量展示、长文本完整渲染；抽样核对无「有数据未展示」情形。
5. 稀疏记录（现状 9 条）完成一轮补充提取或如实报告不可提取原因；新增字段带证据且审计通过。
6. `npm run audit:jobs` 在线通过、`npm run build` 成功、全量回归不退化。
