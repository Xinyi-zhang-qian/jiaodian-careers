# 交点 Careers（jiaodian-careers）

## 软件需求规格说明书

> 版本：V2.0（第 1 轮需求分析，`::req` 生成）
> 输入：用户本轮开发设想（原文见文末附录）+ 代码现状（初版文档由 ::work -explore 基于代码生成）
> 内容边界：本文档只收录用户侧功能需求、架构选择（用户决策层）与性能等约束；设计内容归 docs/design.md 与 docs/interaction.md。

目标系统：面向人文、社会科学与理工科交叉人才的招聘信息静态网站。
目标运行平台：Web 浏览器（静态托管，当前部署于 Render）；数据维护在本地 Node.js 环境完成。
主要使用方式：求职者用浏览器浏览、筛选、收藏岗位；内容维护者通过命令行脚本与规范化数据文件增补、核验、构建与部署。

# 1. 文档目的与系统目标

本文档定义交点 Careers 的软件需求。系统需要提供的能力清单：

1. 公开一个经来源核验的岗位目录，逐条标注核验层级（已核验（逐字段）／已核验（来源）／已核验（关键字段））。
2. 支持按地区、城市、单位类型、岗位类型、学历、学科方向、招聘状态与关键词组合筛选岗位。
3. 为每条岗位提供详情页，展示来源证据（来源页标题、原文片段、获取与核验时间、来源链接）。
4. 提供交叉学科方向浏览与本地收藏。
5. 提供实习岗位线索、机器人与 AI 方向分析、招聘市场观察与机器人岗位样本专题。
6. 提供数据核验管线：提交数据前强制校验来源证据，构建期做离线结构检查。
7. 支持静态导出与静态托管部署。

**本轮新增目标**：

8. 强化数据来源与数据提取的准确性：新增岗位的每个字段都必须可回溯到来源原文，杜绝任何推测性补写。
9. 删除虚假信息：对隔离的历史数据与平台快照逐条回源复核，失效、虚假、无法核实的记录一律不再以任何形式展示。
10. 补充近期北京、上海地区的招聘信息与企业的招聘岗位，重点关注事业单位招聘公告及其报名截止时间，以及企业中项目管理、产品经理、AI 伦理等跨学科岗位。
11. 岗位数据规范化管理：建立便于后续持续增补与更新岗位的数据组织方式。
12. 页面设计进一步优化；项目文档规范化。

系统长期目标：成为交叉背景求职者可信赖的信息入口——宁可少展示，不可展示未经核验或编造的内容。

# 2. 产品定位

系统定位：招聘信息聚合与核验展示站点，不做简历投递、不代理招聘流程，只提供经核验的信息与原始来源链接。

围绕以下核心业务对象组织：

- **岗位（Job）**：一条招聘记录，含身份、条件字段、来源字段与核验字段。类型定义见 `src/lib/types.ts:1`。
- **交叉方向（Discipline）**：平台维护的学科组合标签（当前 11 个），明确区别于公告原文。
- **实习线索（InternshipListing）**：按实习方向组织的实习记录，仅保留已核对来源页的记录。
- **市场样本（RoboticsMarketJob）**：机器人岗位采集样本，带方向分类与薪资标准化结果。
- **条目形态（ListingKind）**：具体岗位、招聘公告、招聘项目三种（由标题推导），用于提示「公告级线索而非单一职位」。

# 3. 用户角色

- **求职者（浏览器访客）**：浏览岗位目录、按条件筛选、查看详情与来源、收藏感兴趣岗位、按报名截止时间安排投递。不需要注册登录。
- **内容维护者（命令行操作者）**：按规范化流程增补与修订岗位数据、运行核验脚本、构建站点、推送部署。
- **运行环境参与者**：
  - Render 构建流水线：执行构建与离线结构检查门禁。
  - 来源网站：核验脚本在线模式实际访问来源页核对原文。

# 5. 架构选择（用户决策层）

既有决策（保持）：

1. **纯静态站点**：`output: "export"`，无后端服务、无数据库；筛选、搜索、收藏全部在浏览器端完成。
2. **数据文件化管理**：岗位数据以文件形式纳入仓库。
3. **数据可信三级核验层级**：所有前台岗位必须带核验层级与可机器复核的来源证据。
4. **Render 静态托管**：提交自动部署。
5. **原页核验锚点强制**：详情页公开展示核验锚点片段。

本轮新增决策（待用户确认）：

6. **数据规范化仍以文件为载体**（用户已确认）：「数据库规范化管理」在本项目语境下指——岗位数据收敛为统一的规范数据源（统一模式定义、统一校验规则、统一的增补入口），保持纯静态架构，不引入需要运行服务的数据库。
7. **文档体系纳入版本管理**：docs/ 三份全局文档与 docs/modules/ 模块文档、docs/test.md 测试注册表随代码一并提交，作为项目文档规范的基础。

# 6. 系统运行需求

- 本地运行：`npm ci && npm run dev`，访问 http://localhost:3000。
- 构建：`npm run build`（prebuild 自动执行离线结构检查），产物在 `out/`。
- 数据核验：提交数据前必须运行 `npm run audit:jobs`（在线回源）。
- 数据增补：维护者通过本轮建立的规范化流程新增岗位（具体流程归设计文档）。
- 运行状态检查：构建成功且 `out/` 生成即为正常；核验失败时脚本以非零码退出并逐条列错误。

# 13. 岗位数据规范化管理（本轮新增）

- 用户可见行为（维护者视角）：存在一个统一的规范数据源与明确的增补流程；新增岗位时不需要人工在多处文件同步修改；ID 冲突、字段缺失、证据缺失等问题在校验阶段统一暴露。
- 数据内容：岗位记录的模式定义统一（含报名起止时间等新增字段）；来源证据结构化保存。
- 边界：规范化不改变前台展示行为与核验层级语义；历史隔离数据的处置通过流程完成而非直接混入。

# 14. 虚假信息清理（本轮新增）

- 用户可见行为：前台不展示任何经复核确认失效、虚假或无法核实的信息；历史隔离数据与未核验快照逐条回源复核，复核结果三分——升级为更高核验层级并保留、降级/修正后保留、下架删除（首轮全量复核与处置已于 2026-11-04 完成；后续新增的隔离数据沿用同一流程）。
- 边界：清理以来源页面证据为准；无法访问来源页的记录不得凭记忆补写后重新上架。

# 15. 事业单位招聘与报名截止时间（本轮新增）

- 数据内容：新采集的事业单位招聘信息必须包含公告发布时间、报名开始/截止时间（原文未提供时不编造）、报名方式；来源优先为政府人事部门网站、单位官网正式公告。
- 用户可见行为：求职者能看到事业单位岗位的报名截止时间，并识别即将截止的岗位。

# 16. 北京、上海近期岗位与企业跨学科岗位补充（本轮新增）

- 数据内容：补充近期（以采集时点为准）北京、上海地区的招聘信息；补充企业招聘岗位，重点是项目管理、产品经理、AI 伦理等跨学科岗位；所有新增记录按既有核验层级规则执行。
- 数量目标（用户已批准）：北京、上海各新增不少于 10 条经核验记录；项目管理、产品经理、AI 伦理等跨学科岗位合计不少于 10 条。

# 17. 页面设计优化（本轮新增）

- 用户可见行为：首页、岗位列表、岗位详情的信息层级、视觉风格与移动端体验得到改善；核验层级等关键信息更加醒目；不改变既有交互逻辑与数据语义。

# 18. 项目文档规范化（本轮新增）

- 用户可见行为（维护者视角）：README 与 docs/ 文档体系保持与代码同步；数据增补流程有章可循（操作指引写入文档）。

# 19. 性能需求

- 用户未提出量化性能指标。现状约束：静态导出、无服务端运行时；构建时逐岗位生成详情页；客户端筛选内存执行、单页 12 条。数据量增长后仍需保持构建时间与页面加载在可接受范围（护栏：构建不因数据量增长而失败）。

# 20. 可扩展性、可维护性与可测试性需求

- 新增岗位通过规范化流程完成，经核验管线校验后生效；流程对后续轮次可重复执行。
- 新增筛选维度、新增字段有明确的扩展路径（归设计文档）。
- 测试现状：5 个模块测试套件经 `npm run test` 聚合运行，全部登记于 docs/test.md；库级回归与视觉验收由 ::ci 执行。

# 21. 验收目标

1. `npm run audit:jobs` 通过（在线模式），全部前台岗位证据可在来源页命中。
2. `npm run build` 成功，`out/` 生成，每条岗位有独立静态详情页。
3. 岗位列表筛选、排序、分页、URL 复现行为与交互文档一致；新增的跨学科岗位与截止时间维度可正常筛选/排序。
4. 前台任何岗位记录均带核验层级与来源链接；「待核实」记录不展示任何条件字段。
5. 隔离数据完成回源复核并有处置记录：保留的记录核验层级如实、删除的记录不再出现在任何前台数据文件。
6. 新增北京、上海近期岗位与事业单位公告，其中事业单位公告含报名截止时间（原文有则必录）；临近截止岗位有可见提示。
7. 新增企业跨学科岗位（项目管理、产品经理、AI 伦理等）不少于 10 条且归类正确；北京、上海各新增不少于 10 条经核验记录。
8. 数据规范化落地：新增岗位经统一流程与统一校验完成，无多处手工同步。
9. 页面设计优化完成且既有交互逻辑不回归。
10. 文档与代码同步，README 含数据增补指引。
11. 收藏、404、来源外链等既有行为不回归。
